# Threat model

> **Status: skeleton (P0.13).** Based on Plan.md §7.1. It gets expanded as the components are built:
> - the Minecraft servers (B4) in **P3** (done)
> - authentication and authorization in **P7** (done)
> - the desktop app (B2, B7) in **P8** (done)
> - the vault and Microsoft accounts in **P9** (done)
> - the control plane in **P10** (done)
>
> It's reviewed as a whole in **P13.7**. Every mitigation listed here must eventually point to the test or control that proves it.

## Scope
The whole afkfleet system:

| Component | Runs on |
|---|---|
| `afkfleet-server` (HTTP API, WebSocket, gRPC control plane, SQLite, vault) | Linux host, Docker Compose |
| Caddy (TLS termination for the HTTP API) | Linux host, Docker Compose |
| `afkfleet-agent` (the bots) | Linux host(s) |
| Desktop app (Tauri) | Users' Windows machines |

Out of scope:
- Minecraft servers themselves
- Microsoft's and Mojang's services
- the security of the host operating systems

Hardening the host is in `docs/runbook.md` (P12).

## Assets
Ranked by impact if compromised:

| # | Asset | Why it matters | Where it lives |
|---|---|---|---|
| 1 | Microsoft refresh tokens | Takeover of the owner's Microsoft/Minecraft account | Server DB, encrypted by the vault |
| 2 | Vault master key, CA private key | Decrypt every stored token; impersonate the server or agents | Docker secrets, outside the DB and backups |
| 3 | User credentials and sessions | Act as any user of the app | DB (Argon2id hashes, SHA-256 token hashes); refresh token in the OS keychain |
| 4 | Control over bots | Chat and run commands as the player, possibly with operator rights on a server | Server (desired state), agents |
| 5 | Chat history and audit log | Privacy of players; accountability | Server DB |

## Trust boundaries
| # | Boundary | What crosses it | Primary protection | Expanded in |
|---|---|---|---|---|
| B1 | Internet → Caddy → server HTTP API | REST, WebSocket | TLS, authentication, `authorize()`, rate limits, input validation | P6, P7 |
| B2 | Webview ↔ Rust core of the desktop app | Tauri IPC commands | Strict CSP, capabilities for our commands only, tokens kept out of JavaScript (ADR-0007) | P8 |
| B3 | Agent ↔ server | gRPC control stream, session grants | mTLS with server-signed certificates, fingerprint allowlist, single-use enrollment tokens | P10 |
| B4 | Agent ↔ Minecraft servers | Minecraft protocol, chat, kick reasons | Untrusted input: sanitized in core, rendered as text, bounded queues | P2, P3 |
| B5 | Server ↔ Microsoft/Mojang | OAuth device flow, token refresh | TLS with certificate checks, no redirects or proxies, bounded answers and timeouts, no retries in the adapter, a single-flight refresh | P9 |
| B6 | Server ↔ storage | DB file, backups, Docker secrets | Secrets encrypted at rest with AAD binding, keys outside the DB, file permissions | P6, P9, P12 |
| B7 | User's machine | OS keychain, installed app | Refresh token only in the keychain, signed updates | P8, P12 |

## Attackers
- **Internet attacker** probing the public API: credential stuffing, enumeration, DoS, injection.
- **Malicious or compromised friend account** (insider): privilege escalation, abuse of bots, reading other users' data.
- **Stolen laptop** with the app installed and a session in the keychain.
- **Compromised agent host:** trying to obtain tokens for bots it doesn't run, or to impersonate other agents.
- **Hostile Minecraft server:** malicious chat or kick messages (injection into logs and UI, resource exhaustion).

## Per-boundary analysis
To be written per boundary (STRIDE: spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege) in the phase listed under "Expanded in" above.

### Authentication and authorization (B1)
*Expanded in P7 (ADR-0006, ADR-0010, ADR-0016).*

**What crosses the boundary.** Every request to the HTTP API, through Caddy's TLS:
- **From the client:** usernames, passwords, invite codes and 2FA codes in request bodies; access, mfa and setup tokens as `Authorization: Bearer`; refresh tokens in a body; IDs in paths and page cursors in query strings.
- **To the client:** an mfa or setup token after the password step, the session's tokens after the code step or a refresh, an invite's code once, recovery codes once, and profiles, sessions, users and invites as lists.
- **The client's address:** the socket peer, or behind a proxy listed in `[http] trusted_proxies` the right-most untrusted `X-Forwarded-For` address. It keys the per-IP limits and is recorded in the audit log.

**What an attacker controls:** every byte of a request (body, headers, path and query), how many requests come and from how many addresses, the timing it measures, and possibly a stolen password, token or laptop. An insider holds a real session with the role of a Member or an Admin.

### Desktop app (B2, B7)
*Expanded in P8 (ADR-0007, ADR-0017).*

**What crosses B2, the webview and the app's Rust side.** The UI calls the 46 commands its one capability grants, and nothing else: no core command and no plugin API, and `withGlobalTauri` is off. tauri-plugin-opener isn't registered: the Rust side calls its free `open_url`, from one command without arguments, on the link it checked (P9.8).
- **Into Rust:**
  - the server's address and a custom CA's certificates
  - usernames, passwords (login, registration, step-up, a new password), 2FA and recovery codes, invite codes
  - IDs and page cursors
  - a username to share an account with, an offline account's name
- **Back to the UI:**
  - profiles, users, invites and sessions
  - the 2FA setup's secret, its QR code and the recovery codes, once each
  - a new invite's code, once
  - accounts and their grants; a Microsoft link's user code and the checked link to Microsoft's page, once per start
  - errors: a closed code with a fixed message and the server's details
  - the live events (P11.8), over one long-running command's Tauri `Channel`: the server's frames as this viewer's REST shows them, why to fetch again, and why the socket went down with its wait; the socket, its ticket and its token stay in fleet-client
- **Never a token.** fleet-client keeps the access token and the login's step tokens in memory, and the refresh token lives in the Windows Credential Manager.
- **Secrets in the UI** live only in the state of the screen that needs them, never in TanStack Query's caches, and go when the screen does.

**What sits on B7, the user's PC:**
- the refresh token, a generic credential in the Windows Credential Manager, one per server origin (`<origin>.io.github.noah-gabel.afkfleet`), stored with Local persistence (this PC only, never roaming)
- `server-profile.json` in `%LOCALAPPDATA%\io.github.noah-gabel.afkfleet\`: the origin and a custom CA's certificates, no secret
- the exe and WebView2's profile

**What an attacker controls:**
- a page the webview might load: it loads only the app's own bundle (the CSP names no remote origin, and the navigation guard refuses every other URL)
- a compromised npm package inside that bundle
- a hostile server's answers, which are rendered as text
- on B7, the PC itself: whoever uses the unlocked Windows account, or malware running as that user

**A stolen or shared PC with a live session (B7).** The app keeps the user signed in, so whoever opens it on the user's unlocked Windows account is that user, without a password.

  - everything that needs no password: the user's profile and sessions, and for an Admin the user and invite lists
  - ending the user's other sessions, and logging out
  - the Microsoft accounts the user may see and their grants; starting a link (active at once at the Owner's PC; accepted risks below), a link again, or an offline account where the server allows them

- **What it no longer gives:** changing the password, replacing the authenticator, every admin write, and every account write but a link need the password within the last 5 minutes. The admin writes are a role change, disabling or enabling a user, and creating or revoking an invite; they need it since Phase 8, group E. The account writes are approving or refusing a link, deleting an account, and creating, changing or revoking a grant; they need it since Phase 9, group E. Setting a bot's server address needs it too, since Phase 10, group E. Releasing a disabled agent's bots over the API and leaving a shared account need it too, since Phase 11, group F (ADR-0020, S49, S51). Guessing the password at the step-up counts toward the username's lockout, which then locks the login too.
- **Malware running as the user can read the refresh token,** as any process of that Windows account can read its generic credentials, and use it elsewhere. - **The remedies:**
  - from another PC, the session list: sessions can't be told apart, so "Log out all other sessions" ends them all, every page included
  - changing the password or replacing the authenticator, either of which ends every other session
  - an Admin disabling the user, which ends every session
  - a session ends 7 days after its last use and 30 days after its login at the latest

### Control plane (B3)
*Started in P10 with which agent runs which bot (P10.5, ADR-0019 S32–S45), the users' calls that reach an agent (P11.2, S48–S51), the session grants (P10.6, S57–S64), the server's ingest (P10.8, S70, U16, U17) and the managed agent's identity, conductor, outbox and link (P10.7, S65–S68), then group H's loopback suite: the real managed agent against the real server, over mTLS on loopback (P10.9, S72), and Phase 10's managed check with a real account (S73).*

**Which agent runs which bot.** Only the server decides, from its own state: an agent's hello never gains it a bot, and its reports count only for the bots the server gave it. Every change of a bot's agent is committed with its own audit entry before the agent hears of it, and a bot leaves its agent only by that agent's word (its `Removed` of a bot the server released, or a hello without the bot) or the host's release of a disabled agent; time never moves it. Two agents never get one Minecraft account: a bot is placed only when no live stream and no release record holds it or another bot of the same account.

**Session grants** (P10.6), the one place Minecraft tokens leave the server. A session request names a bot, never an account. The server answers it only for a bot the asking stream holds assigned, checks the agent's own certificate, the bot's row and whether the bot may run before it asks for a session and again when it issues the grant, takes the account from its own assignment, and answers only on the stream that asked. On the wire the token is only inside `OnlineSession`; on the agent, only in a `SecretString`.

### Minecraft servers (B4)
*Expanded in P3 (ADR-0008, ADR-0010, ADR-0011).*

**What crosses the boundary.** The agent speaks the Minecraft protocol with each server its bots join. It's encrypted only in online mode, with the server's own key.
- **From the server:** chat, kick reasons, game state (chunks, entities) and the timing of every packet.
- **From the bot:** chat and commands, actions, and the account's name and UUID.
- **During an online login,** the agent also calls Mojang over TLS: the session server's join, with the Minecraft token, and the chat-signing certificates.
- **Server names** are looked up through DNS.

A Minecraft server never receives the Minecraft token, and an agent never holds a Microsoft token (security rule 6).

**What a hostile server controls:** every byte a bot receives, and when it kicks the bot or goes quiet. fleet-core's sanitizer and classifier and fleet-mc's adapter treat all of it as untrusted. The runtime's watchdog (P4.6) is the last line.

A mode's on-respawn steps run only after a respawn the agent asked for, after a death it read, which the server confirmed; a Respawn packet without one, a dimension change say, runs nothing (ADR-0020, S22) | P2.9, `bots::chat::an_unlisted_command_needs_manage_on_either_route`, `bots_service::a_line_its_route_doesnt_take_is_refused_before_anything_is_read`, `bridge::a_load_without_a_request_after_a_read_death_confirms_nothing`, `respawn::a_load_while_dead_confirms_nothing_and_the_next_one_alive_does`, `actions::slow_actions_scenario` |
| Elevation of privilege | Code execution through parsing | No `unsafe` in our code (`unsafe_code = "forbid"`). azalea is pinned exactly, its advisories are reviewed (ADR-0012), and a fault stays in its host thread | The workspace lints, `cargo deny`, the containment scenario |

## Accepted risks and known limits
- **Keeping an account locked.** The lockout lets anyone who knows a username keep it locked by failing once per lock: one failure an hour once the lock reached its cap. The user's existing sessions keep working, and an unknown name locks exactly like a real one, so the lock tells nothing about which names exist (ADR-0016).
- **Stale hashes after an `argon2_*` change.** A user who doesn't log in keeps a hash made with the old parameters, so a login for that name takes a different time than the dummy hash, and the name stays distinguishable until they log in once (their hash is re-hashed then).
- **Guessing 2FA codes with the password.** At the default threshold of 5, about 33 wrong codes a day get through (5 free, then locks of 1, 2, 4, 8, 16 and 32 minutes, then one an hour). Each guess matches one of about 3 in 10^6 codes (the window's three steps), so about 1e-4 a day and 3.5 % a year for an attacker who has the password and never stops, while the real user stays locked out nearly all the time. `GET /me` counts the wrong codes since the previous login, without the typos of the login that succeeded (Phase 8, group E), and the app warns about them on Home and in the profile, so the user sees the attempts (ADR-0016).
- **An account without 2FA.** An invitee who registers and never finishes the 2FA setup leaves an account that whoever first logs in with its password enrolls. The app logs in and starts the setup right after registering (P8.7), and the Users screen shows such an account's 2FA as "Not set up", with a hint to disable it (P8.8).
- **No app lock.** The app asks for nothing when it starts: a session in the Credential Manager signs the user in (B7 above). The Windows account's own lock and disk encryption protect the PC, and an Owner's or Admin's PC deserves both. Every sensitive action needs the password again (a step-up).
- **A secret on the clipboard.** "Copy all" (recovery codes), an invite's copy buttons and a link's "Copy code" put a secret on the clipboard, where Windows' clipboard history may keep it; the recovery codes' and the invite's toasts say so, and the text is also on screen to copy by hand. A link's code is worth little once its flow ends (at most an hour, usually 15 minutes), and its toast only says to paste it (the user's text, Phase 9 group F).
- **Displacing a login.** Someone with a user's password can replace the user's live login challenge with a password step of their own, the same class as keeping an account locked.
- **Names an invitee can probe.** Whoever holds a usable invite learns, through registration's "is taken", which usernames exist; the register limit (5 an hour per address) bounds it, and the invite isn't spent by a taken name.
- **Device-code phishing, what's left** (ADR-0018). Approval by someone above the linker counters a friend phishing another friend, but not someone who fools the approver too, nor an Owner who enters a code someone sent them: the Owner's own links need no approval. A victim takes their account back by revoking the app's access in their Microsoft account and having its row deleted. The link screen's warning and the approver's view of who linked which name are the remaining defenses.
- **The Owner's unlocked PC links at once.** Starting a link needs no step-up (ADR-0018, group E), and the Owner's links are active without approval, so someone at the Owner's unlocked PC can add a Minecraft account no one reviews. It still needs that Microsoft account's own sign-in, and it's audited (`account.link`). Locking the PC is the defense, as for the rest of B7.
- **Names a Manage holder can probe.** Sharing an account takes an exact username, and the same 422 for an unknown, disabled or already-managing name still differs from a success; so a Manage holder learns whether a name exists, bounded by 10 tries an hour per user (`grants::granting_by_name_spends_its_own_per_user_limit`), each attempt audited without the name (ADR-0018, group E).
- **Who deletes an Admin's linked account.** An Admin's implicit Manage covers Members' accounts and their own, never another Admin's or the Owner's, so only the Owner (or a Manage grantee) deletes an Admin's linked row. ADR-0018's remedy for a phished victim, "an Admin deletes the row", holds for Members' links; for an Admin's, the Owner does it (`delete::manage_deletes_any_status_and_below_manage_or_unseen_it_is_refused`).
- **The server's host operator creates enrollment tokens without 2FA.** `afkfleet-server agent create-enrollment-token` needs no login, step-up or second factor: whoever can run the binary against the database can enroll an agent. That access already holds the CA key, the vault's keys and the database itself, so it adds nothing. The token is audited (`enrollment_token.create`, `via` = `cli`, no actor) (ADR-0019, U3).
- **Names a token holder can probe.** Whoever holds a usable enrollment token learns, through `ALREADY_EXISTS`, which agent names are taken among enabled agents; the token isn't spent by a taken name, and the enrollment limit (5 a minute per address) bounds it. The name is checked after the token, so nobody without one can probe (ADR-0019, S21), as with invites' usernames.
- **A token's refusals past ten are only logged.** A real token that's expired, used, or whose creator lost the right is audited as an `agent.enroll` Failure at most 10 times, so a flood can't fill the audit log; later refusals appear only at `debug`. Unknown and malformed tokens are never audited (ADR-0019, S17).
- **An admitted agent's connection has no age.** While an agent's welcomed stream lives, its connection may carry up to 15 more calls, which the 80 s age no longer bounds; they still pass their gates. Connections per address aren't counted either: the TLS handshake's 10 s and the age bound each one (ADR-0019, S22).
- **Refused connects past ten a day are only logged.** A known certificate's identity refusals are `agent.connect` Failures at most 10 per agent in a rolling 24 hours; past that a disabled or revoked certificate still in use appears only at `debug` until the window moves (ADR-0019, S30).
- **One slot per agent.** While an agent's stream lives, every other connection with its identity is refused: a thief holding the key can't push the real agent out, but whoever connects first holds the slot until its stream ends, and a restarted agent waits until its old stream ends, at most the heartbeat timeout. A second holder whose twin keeps speaking is audited as `security.agent_identity_conflict`, at most once an hour (ADR-0019, S26).
- **A disable on the server's host takes up to 10 s.** `afkfleet-server agent disable` commits beside a running server, and its sweep ends the live stream within one interval, or two when the disable commits between a stream's hello transaction and its activation (a sweep sees only activated streams); a sweep that can't read keeps the streams until the next. A restored backup can bring back an agent disabled after it was taken: disable it again (ADR-0019, S27, U8).
- **An agent's reports about its own bots are trusted.** A compromised agent can forge statuses and events for the bots assigned to it (S6); reports about any other bot are dropped and counted (ADR-0019, S28).
- **A Paused bot lost to a power loss.** The ingest writes a crossing into or out of Paused or Failed in its next batch (U16), but with WAL's `synchronous=NORMAL` (ADR-0005) a power loss can undo the last commits, that batch included. If the agent loses its memory too (both on one host) and comes back empty, the bot's next agent starts it from an older state and may kick the human who came back to the account once. A server process that dies or is killed loses nothing it committed.
- **Stored chat between two retention runs** (ADR-0020, U19, S45). Each bot keeps at most `[chat] max_lines_per_bot` lines (50,000 by default) and nothing older than `[chat] retention_days` (14), but the task runs once a minute: at the ingest's worst, about 2000 rows a second, the fleet can go up to 120,000 lines over its bounds before the next run, about 0.56 GB at the largest rows. The file keeps its largest size: SQLite reuses freed pages, and nothing vacuums it.
- **What a delete leaves** (ADR-0020, S44). `secure_delete` overwrites what SQLite writes, but a freed page's old image stays in the WAL until the next checkpoint (or the server's stop, which checkpoints), and below SQLite, SSD remapping, the filesystem's journal, a provider's snapshots and deleted files may keep it; backups keep deleted rows for their own retention (P12.3). Encrypting the host's data volume covers what SQLite can't.
- **A crash loses up to an hour of the retention's counts** (ADR-0020, U20). The rows a batch deleted stay deleted, but the hourly `retention.purge` entry that sums them up is recorded only after the hour, or at a clean stop; the gap shows in the next entry's `since`, and the per-run counts are in the log at `debug`. Anyone with the database file can delete or forge rows, summaries included, as for every other entry.
- **A compromised agent can fill its bots' chat.** It can store made-up chat for the bots assigned to it, at its stream's share (1024 rows waiting) and the writer's pace; it can't store chat for any other bot (S28, the insert's `agent_id` guard), and its rows say only what a Minecraft server's chat would.
- **A certificate no agent holds is only logged.** Only someone with the CA's key can make one; its refusal is an `error` line with its fingerprint, never an audit entry, and it's never parsed (ADR-0019, S30, R23).
- **An enrollment the agent didn't store.** If the agent's host can't store its key and certificate after the server answered, the server holds an enabled agent nobody has, and the token is used. When no clear answer comes back after the request may have reached the server (a timeout, a status without the server's request ID, such as a broken connection's `UNAVAILABLE` or the agent's own deadline's `CANCELLED`, or the server's `INTERNAL`), it may. `enroll` exits 3 in both cases and names the agent to disable, or its name when it can't know whether one exists; nothing can use that agent without its key, which never left the host. The server narrows the gap: its deadline ends before its writes, which then run to their end and answer, so its own `DEADLINE_EXCEEDED` means nothing was stored; only the client can still drop the answer of a stored agent, by resetting its stream or with its own `grpc-timeout`.
- **Identity files on Windows.** On Windows, the agent's key and the PKI's keys get no owner-only permissions of their own: they inherit their folder's, so they're as safe as that folder (a folder under the user's profile is readable only by the user, SYSTEM and Administrators). Both commands say so on Windows. Production runs on Linux, where they're 0600 (ADR-0019, S20).
- **A release takes the operator's word.** `afkfleet-server agent release`, or an Admin's or the Owner's release over the API (after a step-up, audited with their name and address; ADR-0020, S49), can't prove that the disabled agent's host stopped: a session that joined before the disable may still be alive on a partitioned host. If so, the new agent's login kicks it once, which Pauses it there, and without a stream it can't come back. A host that's only cut off may also rejoin its disconnected bots with the sessions it kept, until they expire (about 24 h), each kicking the new agent's bot into Paused once. Until someone releases them, a lost agent's bots stay its own and don't run (ADR-0019, S32, S63).
- **The log shows who could have received a token, not who did.** A session grant writes no audit entry (it changes no row): the assignment entries name the only agent that could have received an account's token, while its stream was up, and the server's `info` line per grant narrows it where the logs are kept, but logs rotate and aren't tamper-evident. After an agent is compromised, every account whose bot it held counts as exposed until about 24 h (a token's life) after its last `bot.unassign`, `bot.detach` or `agent.disable` (ADR-0019, S61).
- **A restart that lost a commit, with an agent that doesn't come back.** If the server's host loses its latest commits (a power loss with WAL's `synchronous=NORMAL`, or a restored backup) and an enabled agent that runs a bot whose assignment was lost stays away for 90 s after the restart, another agent may get that bot. The new login then kicks the old session once. Once every enabled agent is back, every bot they run is assigned or fenced (ADR-0019, S45).
- **A bot with an unknown identity is fenced only by its stream.** A hello's bot with no row and no record (made-up IDs) is held releasing, never persisted or audited, so it fences nothing once that stream ends; it names no account the server knows (ADR-0019, S43).
- **A hostile agent can keep its bots and fence those it was given.** A compromised agent can leave its bots running without ever sending their `Removed`, and list bots it was given before so their records fence them. Disable it, then release its bots (ADR-0019, S32, S43).
- **IDs tell when an account was linked.** An account's ID and its bot's are v7 UUIDs whose first 48 bits are the link time, to the millisecond, so View and Control holders can read when an account was linked (and its bot made), which ADR-0018's S11 otherwise shows only to Admins, the Owner and Manage holders as `linked_at`. Nothing else follows from the IDs. The user accepted it (ADR-0019, U10).
- **A server address is checked only where it's dialled** (ADR-0019, S46). Any Manage holder on an account can point its bot at any address that parses, after a step-up; only the managed agent's check right before the dial stands between that and an internal address (P10.7). It can't stop a public address that forwards to an internal one, or a hostile public server (B4 above). Each connect resolves once and dials the socket it checked, so a DNS change counts from the next connect, which is checked again. What a target receives is the Minecraft handshake: the address as written, the port, and the account's name and UUID; an online account's token goes only to Mojang.
- **A listed private network is open to every Manage holder on that agent.** An operator who lists a network in an agent's `[control_plane] private_targets` (a local Minecraft server, the compose stack's bridge) lets any Manage holder of a bot on that agent point it at any address there. It's the host operator's choice, per agent (ADR-0019, S46).
- **The agent's key in tonic's buffers.** The managed agent hands its key's PEM to tonic's `Identity` and `ClientTlsConfig`, which keep it unwiped for the process's life; their `Debug` would print it, so neither is ever formatted. The agent's own copies are wiped (ADR-0019, S68).
- **A notice tonic took can be lost.** An alert or a chat answer the request stream handed to tonic is gone if the connection breaks before the server reads it: the protocol has no acknowledgement. Statuses resync with the next hello; a lost answer reads as unknown (P11.3's note).
- **What the SSRF check doesn't cover.** A network whose only way out is local-use NAT64 (`64:ff9b:1::/48`) can't reach public servers through it, since it's refused; the metadata list beyond link-local holds only AWS's IPv6 and Alibaba's address; a LAN's directed broadcast address inside a listed private network is dialled like any other address there (ADR-0019, S69).
- **Someone at the unlocked PC drives the user's bots.** Reading, starting, stopping, restarting, resetting and resuming the bots the user may Control, and switching their mode, need no step-up, so whoever uses the unlocked Windows account can do them. Each is audited and undone by the next call; a resume or start may kick a human playing the account once, who then pauses the bot again by logging in. A bot's server address needs the password (ADR-0019, S47).
- **Admins read in the audit log what REST hides from them.** `GET /audit` shows every entry to Admins and the Owner through one projection (ADR-0020, S47, R65), so an Admin reads there what the Owner's and other Admins' entries hold: their accounts' Minecraft names and UUIDs (a link, an approval, a deletion, an offline account, a session token's rename), their bots' server addresses and the previous ones (`bot.set_server`), the names of the commands they sent (`command_name`), and the client IP address every entry records, and of the agents, their names and versions, their certificates' fingerprints and the address of the connection that held their place when a second was refused (`live_ip`), though the API hides those accounts and bots from them. The log holds values users typed and servers reported as given, never a secret, a chat line or a command's arguments (ADR-0019, S53; ADR-0010's P7.13 note: the audit log is Admin+).
- **An open app keeps its session alive.** While the app is open and signed in, its live events socket refreshes the session about every 15 minutes (the expected 4001 at each access token's end, ADR-0020, S54), so the 7-day idle end never comes for an app left open, only the 30-day absolute one; it comes once the app is closed. Whoever sits at the unlocked PC with the app open acts as the user for up to 30 days, as they could within 7 before. Locking the PC is the defense, as for the rest of B7 (ADR-0020, U31, the user's choice).
- **A stolen Admin session reads the whole audit log.** `GET /audit` needs no step-up (ADR-0020, S47), so whoever holds an Admin's or the Owner's session, or sits at their unlocked PC, can page through every entry, IP addresses and bots' server addresses included, within the user's rate limit: a full export takes minutes. A step-up would unlock every admin write for 5 minutes and be asked at every refetch; locking the PC is the defense, as for the rest of B7.
- **Session tokens outlive server outages.** A Minecraft session token lives about 24 h, and afkfleet can't revoke one. While the server is unreachable, a bot that disconnects rejoins with the last session its agent was granted for it, in memory, while more than the connect timeout is left (an offline bot with its name); a bot whose session was rejected, or that the server denied, stopped or removed, waits. Past the session's expiry it can't rejoin until the server is back, and an agent that restarts meanwhile holds no sessions. Changes the server can't send meanwhile (a stop, a disabled owner or agent, a deleted account) reach the agent when it's back, as for connected bots (Plan.md §6; ADR-0019, S63). Tested in fleet-agent's `tests/control`: a kicked bot rejoins with its kept grant while the server is down.
- **The session that changes the password keeps its live events socket.** A password change or a 2FA replacement ends every other session and closes their sockets, but keeps the session that made it, and so its socket, as HTTP keeps that session (ADR-0020, S31). Whoever holds that session already sees everything its socket shows.
- **A write from another process reaches open sockets late.** A socket checks its session again after each commit of its own server process. No CLI command changes a session or a role while serve runs, and the access token's expiry closes every socket within one access TTL anyway (15 minutes by default; ADR-0020, S31).
- **A revoked session's socket may get frames for up to 250 ms.** A socket checks its session at most once per 250 ms, and frames aren't held back while a check is owed, so after a revoking commit up to a quarter second of events may still reach it (ADR-0020, R24). Holding them back would let a stream of commits hold them up for good. This is the session alone: what each frame may show follows the rights at once (the row above, R30).
- **A rights change can still meet a frame on its way.** A step checks the commit count after each read it makes, so no frame is built on rights older than a commit already counted (S43). A commit counted after that check, while the frame is built (microseconds), and a frame already handed to a slow client's send (up to 10 s, then 4002), still go out; the next frame is judged on the new rights, a `bot_removed` first.
- **A flood of events on hidden bots can show as one `resync`** (ADR-0020, S40). A socket falls behind the bus's 1024 events only while it's busy (a send, a session check, a read), has events waiting for its rights to be read again after a commit (R47), or has frames waiting, which it sends before it reads the bus again (at most 64 from events, plus one `bot_removed` per bot that left the viewer's sight and one read of the bots it joined, from the gate, R61; each send up to 10 s to a slow client), and the ingest publishes up to 1000 stored lines at once; an agent's reports aren't counted per stream (the accepted "an agent's reports about its own bots are trusted"). What a viewer learns is at most one bit per 5 s: that more than 1024 events were published somewhere, never which bot, kind or how many; fewer leave no trace (`hidden::fewer_hidden_events_than_the_bus_holds_send_no_frame`, `hidden::a_hidden_flood_past_the_bus_shows_only_as_one_resync_without_a_count`).
- **A server's echo of a command shows whole.** S9 cuts command arguments only in the lines the bot sent, a mode's and a user's. What the Minecraft server sends back is received chat, stored and shown whole to every viewer of the bot, View holders included: after `/msg Steve <text>` many servers answer "You whisper to Steve: <text>", and a plugin may repeat what it was given. Whoever can read a bot's chat reads those answers, so secrets don't belong in commands a server echoes (ADR-0020, S9; PR #61's review).
- **Users with Manage act as the player.** That's the purpose of the permission: an insider with Manage on an account can run any command as that player. The audit log records it.
- **Someone at the unlocked PC creates and edits modes.** A mode whose steps send no command off the allowlist is created or edited without a step-up, as the mode switch needs none: its content is what Control already allows. An edit goes through only if the editor could, right then, set the edited mode on every bot that uses it, so it changes nothing on a bot the user couldn't change themselves, and the next edit undoes it; a new mode runs nowhere until someone sets it on a bot, which needs Control of that bot. Deleting a mode needs the password, and a mode a bot uses isn't deleted. A command off the allowlist needs the password on either write (ADR-0020, S16, S17).
- **The pointer tells whether a command is on the allowlist.** `mode_needs_step_up` answers any user who may create the mode, so a Member learns whether a command name is on `[chat] command_allowlist`, which until then only Control holders could learn through chat (ADR-0020, S16).
- **Mode names that look alike.** Names are compared without ASCII case only, so letters of other scripts or non-ASCII case make names that look the same: within one owner's modes they fool only that owner, and only Admins and the Owner make shared ones. The combining marks of scripts that need them (Arabic, Hebrew, Indic) stay allowed, so a name can stack several on one letter, within its 32 characters (ADR-0020, S13, U8).
- **A demoted Admin's shared modes keep counting.** They count toward the 50 modes an owner holds, and their creator can no longer edit or delete them; the Owner can (ADR-0020, S19).
- **Allowlisted commands pass with any arguments.** The allowlist holds command names only, so allowing `/home` allows `/home <any name>`. Only allowlist commands whose arguments are harmless for the player (ADR-0010).
- **Grants outlive a promotion.** An Admin has implicit Manage on Members' accounts and can grant access to others, for example to an alt account created with a Member invite. When that Member is promoted to Admin, the Admin's implicit access ends, but the grants made before stay. Nobody can grant to themselves, which closes the direct path. The Owner reviews them at a role change: `GET /users/{id}/shared-accounts` lists the user's accounts that grants share, `GET /users/{id}/grants` the grants the user holds, dormant ones marked (they count again after a demotion), and the grants route revokes them (ADR-0010; ADR-0020, S50; `grants_review::after_a_promotion_the_grants_a_user_holds_read_dormant_and_after_a_demotion_they_count`, `grants_review::the_owner_sees_the_users_shared_accounts_and_a_revoke_on_the_grants_route_leaves_the_review`). The app's screen for it is P11.9's group J.
- **Chat senders are server-attributed, not verified.** azalea 0.16 never verifies chat signatures, and fleet-mc shows a player message's `unsigned_content` when the server sends one. So a sender's name, its UUID and the text are only what the server claims. No permission or trigger decision may rely on a chat sender; a feature that needs one must verify the signature and use the signed body, in its own ADR (ADR-0011).
- **Plain-text duplicate-login kicks aren't recognized by default.** The classifier only knows the vanilla key `multiplayer.disconnect.duplicate_login`. A proxy or plugin that kicks the bot with plain text when a human logs in makes the bot reconnect and kick the human; the circuit breaker only limits how often. P4.1 adds per-server conflict texts for such servers. They're empty by default, so the user has to configure them (ADR-0010).
- **A hung azalea thread can't be killed.** Each bot has its own host thread and Bevy App with a single-threaded executor, so a panic or a hang affects exactly one bot (ADR-0008 §2–3). A hung thread is abandoned and leaks until the process restarts. Above the abandoned-thread limit the agent exits and Docker restarts it, which briefly disconnects every bot on that agent (ADR-0008 §5, Plan.md §6 row 8). If hangs turn out to be frequent, a process-per-bot connector is the fallback (ADR-0004).
- **azalea 0.16's NBT chat decoder is exponential.** It parses the nested `with` arguments of a translation twice per level, so a hostile server can send a small chat component that hangs the bot's host thread while decoding it, before fleet-mc ever sees it. The hang stays in that bot's thread: the thread is abandoned and counted, and after 3 abandoned threads the agent exits and Docker restarts it (ADR-0011, Plan.md §6 row 8). Removal trigger: an azalea release that fixes the decoder.
- **azalea's trace logs contain secrets.** Both binaries cap `azalea_auth` at `info`, whatever the operator's filter says, and a redaction test checks each cap (ADR-0011).
  - **Agent:** in every online session, azalea fetches the account's chat-signing certificates with the Minecraft token, and `azalea_auth::certs` logs the whole response at `trace`, the chat-signing private key included. The agent's filter keeps azalea's targets at `warn` by default, and the cap holds even when the operator asks for more (P5.2). fleet-mc's own code never logs the token; a redaction test captures every level from every target to check that.
  - **fleet-server:** its Microsoft flows don't use azalea-auth: the adapter sends its own requests (ADR-0018), and `deny.toml` keeps azalea-auth out of it. The cap stays as a guard, and a test checks it on the server's layer with the filter at `trace`, from the config file or the environment. The adapter itself logs one `debug` line per failed call, never a body, a header, a token, a code, a name or a UUID; its redaction test checks every level of every target.
- **tungstenite's trace logs contain every live events frame.** tungstenite logs each WebSocket frame it reads or writes at `trace` (a text frame's text in the clear, chat lines included) and a close frame's reason at `debug`, on the server since P11.5 and in fleet-client since P11.8. fleet-startup's filter caps `tungstenite` and `tokio_tungstenite` at `info` beside `azalea_auth`, outside any binary's rules, so no operator's filter lifts them; tests check the cap on the server's and the agent's layers (ADR-0020, S56). The ticket and the bearer never reach these lines at all: fleet-client's handshake is reqwest's own upgrade, so tungstenite's client handshake, which logs the whole request, never runs (U25). The desktop app installs no log subscriber, so nothing logs there.
- **Minecraft servers aren't authenticated.** The Minecraft protocol doesn't prove a server's identity: it encrypts with the server's own key, without a certificate. So whoever controls DNS or the network path between an agent and a server can pose as that server.
  - The Minecraft token never reaches a Minecraft server, only Mojang's session server over TLS. In online mode Mojang binds the join to the server's key, so an impostor can't pass the bot's login on to the real server.
  - The impostor still gets everything the bot says and does there. That includes anything users send through the bot's chat, such as `/login <password>` for a server's login plugin.
  - **Offline accounts have no protection at all:** the connection isn't encrypted, so anyone on the path can read and change it, and anyone can join under the bot's name (ADR-0008, ADR-0011).
- **A server can grow a bot's memory.**
  - azalea caps a single packet at 8 MiB uncompressed and checks the declared size before decompressing (azalea-protocol 0.16.0). Nothing caps the World a server fills with chunks and entities, and fleet-mc doesn't limit a bot's memory.
  - The agent container's memory limit (P12.2, planned) and Docker's restart (Plan.md §6 row 10) bound it, which briefly disconnects every bot on that agent.
  - If this turns out to happen, a process-per-bot connector is the fallback (ADR-0004), as for hangs.
- **azalea's resolver may fall back to Google's DNS.** azalea looks server names up with hickory and the system's resolver configuration. When the host has none, it queries Google's public DNS instead, which then learns which server names the agent resolves. Server addresses that are IP addresses are never looked up. The connect timeout bounds every lookup, since azalea's resolver has none (ADR-0011).
