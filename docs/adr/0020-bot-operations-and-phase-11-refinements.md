## Context
Phase 11 makes the fleet usable from the app day to day: chat, modes, live events, retention, the Tauri side of the events, the screens, dark mode and a design pass. Phase 10 built P11.1 and P11.2 already (ADR-0019, U1), and left one follow-up for Phase 11's first group: U24, a refused login's next session request stays fresh.

The plan read the code first. Nothing builds `ServerMessage::SendChat` yet, the modes port only finds one mode, there's no `/events`, no `GET /audit` route, no retention job, and `agent release` is CLI-only. fleet-client has bot methods only, and the app has no bot, mode, agent or audit screens.

Every open question went to its own read-only review agent, given the options neutrally (CLAUDE.md's step 10). The user approved their decisions (S1–S6) at the plan review, with one addition of their own (U1). Each later group asks its own questions in its session and adds its decisions here.

- **Approved at the plan review:** the thirteen groups; S1–S6; the chat limits' ranges and defaults (rule 10: `chat_per_bot_interval_secs` 1–60, default 3; `chat_per_bot_burst` 1–10, default 3, lowered to 1–8 at PR #59's review, U2; `chat_per_user_per_min` 1–60, default 20); the runtime's chat-quota test moving to fleet-core's `ChatRate` with the setting it tests (S3); the `/me` step of `just test-real-account` expecting fleet-mc's refusal (S2); and B's three error texts as drafted:

  - `chat_unavailable` (409): "This Minecraft server only accepts signed chat, and the bot can't sign this message. Commands with a message, such as /msg or /me, can't be signed."
  - `command_needs_step_up` (403): "This command needs your password: confirm it's you to send it."
- **U1. The DoD checks with real accounts get a data folder of their own** *(the user's addition at the plan review)*. Linking a real account stores its Microsoft refresh token in the server's database, sealed by a vault key file that sits right next to it.
  - Both checks (H's first, M's 24-hour run) use one folder, `target/dod-run/`: its database, its vault key, its PKI, the agent's identity and the logs. They run through recipes of their own, which H adds, never the everyday `target/dev-server/`, so the account linked in H can stay for M.
  - They log at the default `info`, so no chat text is written to disk (chat is logged only at `debug`). A default-profile test pins the recipes' filter.
  - A cleanup recipe deletes that whole folder when the user is done. A default-profile test proves it removes everything inside and touches nothing outside: the other folders in `target/`, a file beside it, and a link inside it that points outside, which it removes without following. It refuses any other path.
  - The steps say: unlink the accounts in the app first, then run the cleanup, then optionally end the app's consent in the Microsoft account.
  - This mirrors production, where the key file lives on the server's host next to the database it seals; `target/` is never committed.
- **U2. `chat_per_bot_burst` is 1–8** *(the user's decision at PR #59's review; the default stays 3)*. Vanilla's chat throttle (`TickThrottler`) adds 20 for each chat message or command and kicks with `disconnect.spam` once its count is no longer below 200, losing 1 a tick, so 10 messages within one tick are kicked: S3's "10 stays under the spam kick" was wrong. The agent enforces the rate too, so the largest burst a server may set has to clear the throttle. A slow test proves it on `just test-slow`'s vanilla 26.1 server: a full burst of `ChatRate::MAX_BURST` sent back to back echoes every message and is never kicked (`actions::slow_actions_scenario`'s `chat_burst` step). The same step with 10 and with 12 messages was kicked for spam, each run once and reverted.

### Decided by the review agents *(approved by the user at the plan review)*
One read-only agent per question, each given the options neutrally.
- **S1 (security). U24 lives in fleet-core's state** (ADR-0019, U24: "after a refused login, a bot's next session request stays fresh until a fresh grant arrives").
  - `BotState::Backoff { attempt, fresh }`. `session_unavailable` carries `AwaitingSession.fresh` into the backoff, and `retry_due` asks with it. `restore` keeps it for `AwaitingSession` and `Backoff`, and gives false for `Connecting` and `Online`, where a grant had arrived. `session_ready` turns it into `Connecting { auth_retried: fresh }` as before, which ends it.
  - Every backoff entered from `Connecting` or `Online` is non-fresh; an `AuthInvalid` while Online stays transient (ADR-0010), so a Minecraft server can't drive Microsoft refreshes. Start, Stop, Reset, Resume, a restart and a server change begin non-fresh, as before.
  - The proto's `Backoff` gains `bool fresh = 2`; `PROTOCOL_VERSION` stays 1 until the first release (ADR-0019, S9). No database, DTO or `ManagedCredentials` change: the server stores only the state's name, and the agent already wipes a kept grant on a fresh request and never hands one to it (S63).
  - *Consequences:* a fresh grant after a backoff that's refused again ends `Failed(Auth)`, which is §6 row 5's one fresh token; a refused request isn't a token. S58's limit still fits: with the default backoff, about six fresh requests fall in the first five minutes, the burst, then at most one per 10 minutes reaches the token service and the rest are denied retryably with the bot still fresh. Requests without a stream fail at the agent and never spend it.
  - *Why:* lifecycle state goes through `transition()`; the flag survives the supervisor's restore after an actor crash, which reads the published state; it's U24's wording exactly; fresh requests stay visible to the state machine, as S62 required.
  - *Rejected:* also across Stop then Start and the sticky states (overturns ADR-0010's "`Reset` from `Failed(Auth)` asks for a normal session", and puts fields on four more states and the stored sticky state, against at most one more refused join per deliberate action); the flag in `ScheduleRetry` and `RetryDue` (a crash during the backoff loses it); the agent's provider upgrading requests (the state machine would read `auth_retried: false` and a second refusal would loop; S62 rejected hiding a refresh from it); the server dropping its cached session on a reported refusal (the request still wouldn't be fresh, and a compromised agent could force refreshes outside S58's limit).
  - *The agent waits longer than the server may take* (PR #59's review): with U24 every retry asks fresh, and a fresh request takes only a session minted after it arrived, so an agent that gave up before the server answered would ask again, never take the session the server had just minted, and spend S58's budget while Microsoft is slow, until the bot failed. The runtime's `session_request_timeout`, which the managed provider's wait follows, goes from 30 s to 150 s: above the session-token service's `WAIT_BOUND` (2 minutes, the wait for the account's flight and the flight itself, the adapter's 60 s session included) plus 20 s for the grant's reads, its fenced write and the hop. `timing::the_agent_waits_for_a_session_longer_than_the_server_may_take` (fleet-integration) pins the relation over the constants.
  - *Residuals:* a deliberate restart, a server change or an agent restart after a refusal asks once without `fresh`, and so does a bot removed and added again, or moved to another agent: its new actor starts non-fresh. Each can cost one refused join before the normal fresh retry. A request queued behind other bots' grants on a busy stream can still outlast 150 s while Microsoft is slow; it then fails retryable and asks fresh again.
- **S2 (security). Secure chat: refuse what the server would reject, judged by its own command tree** (P11.3's flagged note; ADR-0011's "Commands: a known limit, not decided"; ADR-0013's mode chat "through `ChatUnavailable`").
  - Wherever fleet-mc's `needs_signing` holds (an online account, an authenticated join, a server whose login packet enforces secure chat), a command whose name (`ChatMessage::command_name()`, the name the allowlist uses) can reach a `message` argument in the server's command tree is refused before it's sent, with the existing `SessionError::ChatUnavailable`, even when the session signs chat.
  - The reachability follows children and redirects but never a redirect to the root, as vanilla's own check stops at the root: `/execute … run` isn't caught, while `tell`, `w`, `tm` and `minecraft:` forms are. It's one backward pass from the message nodes with a visited set, ignoring indexes out of range, and each of the root's children is named once however often the root lists it, so the cost stays linear in the packet: each node visited once, each name copied once (PR #59's review, below). Until a tree arrives, commands go out as before, as the vanilla client does with an empty tree.
  - User chat gets `ChatFailed{ChatUnavailable}` through the existing path; mode chat is skipped at `debug` as before. No wire and no runtime change. fleet-mc warns once per session about a refused command, in its own words, never the command.
  - *Why:* the vanilla client decides what to sign from this same tree, and the server checks against its own copy, so this refuses what the server would reject, and slightly more: a command whose name reaches a `message` argument anywhere is refused whole, so `/kick` and `/ban`, whose reason is an optional message, and an incomplete `/msg` without its message are refused too, though vanilla would take them unsigned. A plugin's `/msg` with a plain text argument still goes out. It ends `Ok` for chat the server drops, the bug the user's P3.7 fix ruled out, and an ERROR in the server's log for every repeating `/me` of a mode.
  - *Rejected:* signing commands (azalea 0.16 has none, "TODO: commands that require chat signing"; it needs a brigadier parse of argument types and azalea's signing internals, and a wrong signature can disable the session's chat; it can be built on this tree later); a fixed list (refuses plugin commands that work unsigned, misses datapacks', and needs updating per Minecraft version); refusing at the API (breaks `/msg` where nothing is enforced and overturns ADR-0013's decision); keeping the limit.
- **S3 (security). One chat rate per bot, the server's, sent in its spec** (P4.5's note: "decide where that setting lives (server settings, sent to agents)").
  - fleet-core's `chat::ChatRate`: an interval of 1–60 s and a burst of 1–8, 3 s and 3 by default, refused and never clamped. *(Corrected at PR #59's review, U2: the burst stopped at 10 "to stay under vanilla's spam kick", but 10 messages in one tick are kicked; the agent enforces the value too, so it stops at 8.)*
  - `BotSpec.chat_rate` (proto: a `ChatRate { interval_secs, burst }` message, field 7). The server's `[rate_limits] chat_per_bot_interval_secs` and `chat_per_bot_burst` fill it in the reconciler's specs; standalone agents use the default, and `agent.toml` gets no key.
  - The agent's runtime builds each bot's bucket from its spec and swaps it in place when an update changes the rate (behind a std mutex, never held across an await); an equal rate keeps the bucket. *(Corrected at PR #59's review:)* a change never refills it: the new bucket keeps what the old one held, up to the new burst. The runtime's fleet-wide `chat_interval` and `chat_burst`, and `FleetSetupError::ChatQuota`, go; the zero-interval test moves to `ChatRate`.
  - The HTTP limits are B's: `chat_per_user_per_min` (keyed by the user), then the per-bot rate (keyed by the bot), spent after `authorize()` whatever the outcome, so a 429 never reveals a bot (as S52). An agent's `RateLimited` reaches the user as the same 429.
  - *Why:* the user's Phase 4 answer named "server settings, sent to agents", and Appendix A plans the keys; one source keeps both ends equal, so §7.4's "all configurable" works both ways; the agent's bucket is the only guard that sees mode and user chat together before the Minecraft server's spam kick.
  - *Rejected:* a fixed, independent agent default (a looser server gives successes followed by agent refusals, so the real rate could only be lowered); an `agent.toml` key (two hosts to keep in sync, against "server settings"); enforcing only on the server (overturns P4.5's shared bucket and leaves mode chat unguarded); the rate in `Welcome` (a fleet-wide setter, applied before the reconcile, and no per-server rates later).
- **S4 (security, built in B). Step-up for chat:** `POST /bots/{id}/chat` (authed) takes plain chat and allowlisted commands (Control) and never sends a command off the allowlist, even after a step-up: a Manage holder gets 403 `command_needs_step_up`, before any chat limit is spent, and the app resends through `useStepUpAction` to `POST /bots/{id}/command` (a step-up route, any command, Manage).
  - *Why:* S47's test. An unlisted command fails all three of its conditions: `/op` widens access on a Minecraft server, `/pay`, `/clear` and `/give` lose things, and nothing undoes them. Plain chat and allowlisted commands pass. The Owner and Admins hold implicit Manage on many accounts, so an unlocked PC or a stolen refresh token could otherwise `/op` someone on every server where those accounts are operators.
  - *For C (P11.4):* writing the text of a command off the allowlist into a mode needs a step-up too; switching to an existing mode stays as S47 has it (its text is fixed), recorded as an accepted risk.
  - *Rejected:* no step-up for chat (the most dangerous bot action left open); a step-up for every command (prompts for `/spawn`, and disagrees with the mode switch); a step-up for all chat (a password to say hello); one route that answers `step_up_required` itself (checks the stamp in an authed handler, against rule 1 and the user's "checked by the extractor only", ADR-0016).
- **S5 (security, built in B). The send's answer.**
  - One write transaction re-reads the actor, the bot and the grant, authorizes again, and judges reach (fleet-core's new `judge_chat`, table-tested like `judge_command`): no agent, desired Stopped, or held without an Online report is 409 `bot_not_online`; an agent not Online or a bot not held is 409 `bot_unreachable`. A refusal writes and audits nothing.
  - Otherwise it mints the `ChatRequestId`, appends the row (S6) and commits the entry, all before anything is sent. Then it subscribes to the bus and sends through a new `LiveAgents::send_chat`, checked and queued in one critical section as `command` is.
  - It waits outside any transaction until the earlier of the send plus 6 s and the handler's start plus `request_timeout` − 2 s. It matches the request ID, the bot and the agent, not the generation, since an answer may come on a later stream.
  - *Answers:* 200 `sent`; 202 `pending` when nothing came or the subscriber lagged; `NotOnline`, `Disconnected` and `NotInWorld` 409 `bot_not_online`; `ChatUnavailable` 409 `chat_unavailable`; `RateLimited` and `QueueFull` 429 `rate_limited` with `Retry-After` the per-bot interval; `TimedOut`, `SessionBusy`, `AgentBusy`, `UnknownBot` and `ShuttingDown` 409 `bot_unreachable`; `Unsendable` 500. The match has no wildcard. The body is `ChatSendResponse { request_id, message_id, outcome }`, `outcome` an `Open<sent | pending>`.
  - *Why:* S3's 429 and S2's error need the agent's answer, and ADR-0019's group G note planned a bounded wait ("one that never comes reads as unknown"). Refusals and `ChatSent` come within milliseconds, and fleet-mc's 5 s job timeout fits, so `TimedOut` comes back as an answer.
  - *Rejected:* no wait (no feedback before P11.8); a wait for refusals only (S2's refusal is a delivery failure); a wait of about 12 s (handlers held longer, and a slow database pushes the answer into a 408).
- **S6 (security, built in B). A user's message is a chat row; its audit entry holds no text.**
  - A `chat_messages` row, direction `out`, kind `user`, appended in the send's audited transaction through the existing guarded `append`, with the agent reach found; `None` rolls back as 409 `bot_unreachable`. No migration: `kind` has no CHECK, and an outgoing row has no sender and no cut. No sender column: the audit entry names the actor and the row.
  - *Field rule:* an outgoing command row shows its arguments only to Manage holders; everyone else sees `/name`. Mode rows follow the same rule. A `/login <password>` in the history mustn't reach View holders.
  - *The audit:* `bot.send_chat` and `bot.send_command`, one per route; the actor, the IP, `AuditTarget::Bot`; metadata `request` (the `ChatRequestId`), `message` (the row's ID), `command` (`none`, `allowlisted` or `unlisted`) and `command_name` only when `allowlisted`. Never the text or its length.
  - *Why:* ADR-0016's metadata rule allows names from closed sets and values the server made, never text a client sent; Admins read the audit log while other Admins' and the Owner's bots are hidden from them; commands can carry passwords; and with no text in the audit, retention really deletes what users said. Accountability stays: who, which bot, when, which route, whether a command.
  - *Rejected:* a row only once `ChatSent` arrives (the text would wait in memory, and the ingest's `EventBatch` would carry a user's decision, which widens U17 in substance, the user's); no row (the console would show replies without what was asked); the text in the audit (above).
  - *The user's, at B's planning:* whether the console names who sent each line, and to whom. A column can be added and backfilled from the audit entries' `message` key later. Unlisted command names or text in the audit would loosen ADR-0016's rule, also the user's.

- **S28 (security). `GET /events` needs the session's bearer token and the ticket** (`authed_route`, class Standard). The ticket must have been issued to this very session, so a leaked URL alone (a proxy's log, a crash report) is worthless, and cross-site WebSocket hijacking can't happen: nothing here is a cookie, and a browser can't set `Authorization` on a WebSocket. Every bad ticket (malformed, unknown, used, expired, another user's or another session's) gets one 404 `not_found`, identical but for the request ID, with one `debug` line naming the reason, never the ticket.
  - *Not 401:* fleet-client reads a 401 as an expired access token, refreshes, and ends the session after the retry; a 404 is what a personal resource that isn't the caller's already answers (P7.8).
  - *The ticket is spent only by a real upgrade:* a request that isn't one is refused by the upgrade's own checks first.
  - *Rejected:* the ticket alone on a public route (a credential-bearing route on the allowlist, which the 401 test can't cover; a second authentication path beside `authenticate`; a leaked URL usable for 30 s); a new route kind (the user's, and not needed).
- **S29 (security). Event tickets live in memory, in `app::event_tickets::EventTickets`, built like the login's `Challenges`; no moka.**
  - A std `Mutex<HashMap>` keyed by the ticket's SHA-256 (a lookup, then `ct_eq`, as the sessions' access hashes are found), each entry `{hash, user, session, issued_at}` on the server's `Clock` (`ManualClock` in tests). The first presentation takes it out under the lock, whoever presents it, so two connects with one ticket can't both pass. Expired entries go at every issue and take, and in housekeeping's purge. A user holds at most 3; a fourth evicts their oldest.
  - `TokenKind::EventTicket`, prefix `afk_wt_` (`afk_et_` is the enrollment token's), 32 bytes from `SecureRandom` (getrandom); `fleet_core::auth::EVENT_TICKET_TTL`, 30 s.
  - `POST /events/ticket` (authed, Standard, no body) asks `authorize(UsePersonal, Personal{owner})` and answers 200 `EventTicketResponse {ticket, expires_in}`, like `MfaResetResponse`. Its limit is the per-user limit every authed request spends (10/s, burst 30), with the per-user bound on what a user holds. No audit entry: nothing stored changes, as with a 2FA replacement's challenge.
  - The app never sees a ticket: fleet-client mints one per connect (G).
  - *Rejected:* moka (its clock isn't the `Clock` port, so the 30 s would need a real-time test or this same check anyway; no per-user bound; its admission can evict another user's ticket); refusing at the per-user bound (a leaky client locks itself out); a table (a write per connect, and a secret persisted); a rate key of its own (no outside cost to protect against a 256-bit secret).
- **S30 (security; built in D2). Rights at send time come from one shared snapshot, rebuilt after any commit.** `BotReads::access()` reads, in one read transaction, every bot with its account's owner, every grant, and every user's role and enabled flag (unpaged, as `fleet()`). `app::events::LiveRights` keeps the latest snapshot, tagged with the commit count it was read at; a socket that sees the count moved asks for one at least that new, and a tokio mutex runs one rebuild at a time. An event about a bot the viewer can't see is dropped by a hash lookup: no read, no frame, no count. The projection lives in `http/handlers/events.rs`, a child of `handlers`, so `chat_line`, `mode_response` and `account_response` stay private there.
  - *Rejected:* a read per event (about 40,000 joins a second at the ingest's worst case on 4 read connections shared with the API, and a flood on a hidden bot would show as lag); a cache per socket (20 rebuilds per commit); explicit invalidation calls from about 60 commit sites (a missed one leaks); a cache with a TTL (not "at once").
  - *Residual:* a CLI command run in another process doesn't count; none changes a user's rights while serve runs.
- **S31 (security). An open socket re-checks its session after every commit, and lives at most until the access token it connected with expires.**
  - `TokenService::check_socket` re-reads the session by ID with its user (`SessionReads::find`) and applies fleet-core's `access_decision` to the session's times as the connecting request saw them (`AuthUser` carries them), and refuses a changed role, which always revokes anyway. A refusal closes with 4001.
  - A deadline at the connecting token's access expiry (`refreshed_at` plus the access TTL, capped at the absolute expiry) closes with 4001 without a read. The app reconnects about every 15 minutes, which makes it refresh, so a stolen and rotated refresh token is caught within one access TTL by the reuse detection.
  - A password change or a 2FA replacement keeps the session that made it, and so its socket, as HTTP keeps that session.
  - *Rejected:* a registry of sockets that six revocation paths must remember to call (and none sees a write from another process); periodic polling (late, constant load); the absolute or idle expiry only (a socket for days with no proof of the refresh token); re-reading `refreshed_at` (a thief's refresh would extend the victim's socket).
- **S32 (security; built in D2). Every bot event carries the whole `BotResponse` this subscriber would get from `GET /bots/{id}` now** (`BotService::view`, `authorize(ViewBot)`, `bot_response`: the shown state, `agent` only for Admins and the Owner, `server_address` only for Control and above). A server-decided change publishes a fact-free hint, `Bots([BotId])`, after its commit: start and stop, a sticky state cleared, `PATCH`, `PUT` mode, an account deleted, refused or approved, a link's commits, an offline account created, a session-token status, a grant set, changed or revoked, and the reconciler once per pass for the bots whose assignment, hold or agent changed. A socket merges what's pending, reads each bot it may see and sends `bot`; a bot it showed that is now refused or gone gets `bot_removed`. `Died` and `Alert` become `bot_died` and `bot_alert` after the same check. No sequence numbers: a filtered event leaves no gap.
  - *Rejected:* a status-only kind (two shapes, the same read); an invalidation-only event (a refetch storm against the per-user limit); facts about who could see a bot carried in each event (every publisher would have to capture them).
- **S33 (security; built in D2). A mode event carries `{id, was}`, and each socket re-reads the mode when it sends.** `ModeService::create` (and its twin), a real `update` (after its `Change::Store`) and `delete` publish after their commit; a no-op or a refusal publishes nothing. `was` is the mode's context as the transaction read it (owner, the owner's role, visibility). Per subscriber: sees it now → `mode` through `mode_response`; saw it before, judged on `was` → `mode_removed`, the same for a delete and a loss of view; otherwise nothing. A real role change publishes `RoleChanged`, and every other subscriber who is an Admin gets `resync`.
  - *Rejected:* the committed `ListedMode` on the bus (a stale owner role, late events after a delete, command arguments held in the bus); separate deleted and hidden kinds (they tell a viewer that a hidden mode exists); no create event.
- **S34 (security; built in D2). Chat events.** The user's line is published right after its commit and before the stream send, with the request ID; a send refused after the commit publishes `ChatNotSent`, sent as `chat_failed` with `bot_unreachable`, the 409 the sender got. **A failure's reason only for subscribers at Control and above**, as one of four coarse codes equal to the `POST`'s answers (`bot_not_online`, `chat_unavailable`, `rate_limited`, `bot_unreachable`), from one exhaustive function beside `chat_line` that `chatting` shares; View holders get `chat_failed` without it (left out, S54). `chat_sent`, `chat_failed` and the request ID go to every viewer of the bot.
  - *Rejected:* every viewer (facts a View holder can't act on, such as a server enforcing secure chat, whose address they don't see); the sender only (Admins and Manage holders watching couldn't tell why); the raw proto reasons (finer than S5's answers).
- **S35 (security, DoS). The socket's limits and lifecycle** (values: U13).
  - *The cap* is taken before the upgrade: a `SocketSlot` counted under one std lock, released by its `Drop` on every end, a panic included. Over it, 429 `too_many_connections` with `Retry-After: 45`, the longest a dead socket of theirs can hold a slot.
  - *What the client may send:* only a pong answering a ping, and a close. Anything else (text, binary, a ping, an oversize frame, a protocol error) closes with 1008. A lost connection is told from a refused frame by an `io::Error` in the error's sources.
  - *The outgoing side:* the bus's receiver is the queue. One frame is in flight, `write_buffer_size(0)`, `max_write_buffer_size` 128 KiB, and each send runs within 10 s, else 4002. `Lagged` sets one pending `resync`, without a count, sent at most once per 5 s; a lagging socket is never closed (that turns a flood into a reconnect loop).
  - *One task per socket* over axum's own `recv` and `send` in a biased `select!`, sends in branch bodies: no futures-util in the server's code.
  - *Shutdown:* `LiveSockets { TaskTracker, stop }`, shaped like gRPC's `Sessions`. Each socket sends 1001 within 1 s; serve waits for them within the drain, before the database closes.
  - *Logs:* one `info` line when a socket opens and one when it closes (why, the code, how long), never the ticket; the cap's refusals counted in the minute's summary. `SocketTimings` carries every bound, so tests run them short on real sockets.
  - *Rejected:* the cap after the upgrade (a spent upgrade and task per refusal); reusing `rate_limited` (the app couldn't say why); evicting the oldest socket (two devices taking turns); a dispatcher with a queue per socket; closing a lagging socket.
- **S36. The wire: one flat `EventMessage` in `fleet_api_types::events`, documented as `OpenAPI` components.** `{type: Open<EventMessageKind>, …optional fields}` (S12 and S54's flat DTOs), a response only, one JSON text frame each. The first frame is `ready`, sent once the socket subscribed to the bus, so a client fetches its snapshots after it. The types join `components()` and the TypeScript export, so the equality tests cover them; `GET /events` is in the document with its 101, its `ticket` parameter and an `x-websocket-message` extension naming `EventMessage`. The protocol (frames, `ready` and `resync`, pings, sizes, close codes, and a client's three reading rules: an unknown `type` is ignored; a known one missing a field its kind always carries, or a frame that doesn't read, is a resync; kinds and fields are only ever added) lives in the module's docs.
  - *Rejected:* one struct per kind, or a tagged enum (`oneOf`, which the renderer refuses, and an unknown tag fails the whole frame); TypeScript-only like `app` (wire types aren't IPC types); an AsyncAPI document (a second artifact to keep in step).
- **S37. Hands-on: an `events` verb in `just dev-bots`**, printing each event in the console's line formats (never a mode's steps) until Enter; no new recipe.

### PR #66's review, fixed on the branch
Thirteen points, in eight commits before the docs. Each fix's test was shown red first: against the old code or a stub, or, for a test that pins working code, by a temporary mutation restored from a saved copy and checked by checksum.

*The user's decision at PR #66's review (CLAUDE.md step 10's second case: R16 against ADR-0017's "no token of any kind leaves fleet-client"):*
- **U15. R16's bearer exception holds for the dev console alone, and is enforced.** `Client::events_handshake` and `EventsHandshake` exist only with fleet-client's non-default `dev-console` feature, which only `just dev-bots` enables (and fleet-client's own tests, through the crate's dev-dependency on itself), so the desktop app can't call it. G opens the app's socket inside fleet-client (tokio-tungstenite becomes its normal dependency there, as Plan.md §5 planned), so the token never leaves it, and removes the feature and the exception. It stands next to ADR-0017's rule, which is otherwise unchanged.

*My choices in the fixes (the review named what to fix):*
- **R22. A connection that ends without a close frame is told by its error's text.** tungstenite reports it as `Protocol(ResetWithoutClosingHandshake)`, and fleet-server reaches tungstenite only through axum, so `classify` compares each link of the error's chain with the text "Connection reset without closing handshake". A unit test builds the real tungstenite error, so a bump that changes the text fails. *Rejected:* a direct tungstenite dependency for a typed match (a new dependency for one match); every protocol error taken for a lost connection (a client's breach would be logged as a loss).
- **R23. The commit count moves for every commit asked for, and once more after a dropped one landed.** A commit takes a turn (`infra::sqlite::commits`) that moves the count when dropped, however the commit ended, and marks the count unsettled until its `COMMIT` returned. While the mark stands, the write pool's `after_release` pings the returned connection, which answers only after everything it was handed ran (sqlx 0.9 runs `after_release` before its own ping, and one worker thread runs a connection's commands in order), and moves the count again. So a socket woken before a dropped commit's `COMMIT` landed is woken once more after it. *Rejected:* the guard alone (a socket could read the old state just before the commit lands, and nothing would wake it again); a task spawned from `Drop` (no owner, and no runtime is guaranteed there).
  - *Amended in group D2's first commit (S38, S39, below):* the mark is the generation of the commit that set it, and a commit's return clears only its own. `Transaction::commit` drops the connection inside its last poll, which spawns sqlx's return of it, so another worker can settle the commit, hand the connection on and start the next commit before the first one's future sees its `COMMIT` return; a shared flag let that late return clear the next commit's mark. And the write pool has no lifetime: sqlx 0.9 closes a returned connection past it, or one returned to a closed pool, without running `after_release` (`Floating::return_to_pool`), so a commit dropped on a write connection older than 30 minutes (sqlx's default) never got its settling move. A closed pool has no socket left to wake: serve stops the sockets within the drain before the database closes. A sqlx bump re-reads that function.
- **R24. A socket checks its session at most once per 250 ms (`CHECK_GAP`), and nothing waits for the check.** The count is read at every turn, whichever branch woke the loop, so no busy branch hides a commit; a move within the gap is checked when the gap ends. The client's frames, the idle close and the ping tick come before the check in the biased `select!`. Frames (`resync` now, D2's events later) aren't held back while a check is owed. *A change to R18,* which said a moved count runs the check before any frame: a frame can now go out up to 250 ms after a revoking commit (the threat model's accepted risk). Holding frames while a check is owed would let a stream of commits hold them up for good. `ResyncGate` became `Gap`, which serves both.
- **R25. R20 as built.** Each send races the stop: once it fires, the send gets the close bound (1 s) to finish, else the socket is dropped without a close frame (`Ended::Abandoned`, logged as "a send was stuck when the server stopped"); the session check is given up at once with 1001; the close frame and its drain share one close bound. The connect takes the tracker's token first, answers 503 `busy` once the stop is cancelled, and races its own check against the stop.
- **R26. A user holds as many unspent tickets as they may open sockets** (`EventTickets::with_per_user`, which serve sets from `ws_connections_per_user`; 3 by default).
- **R27. Tests that need a client that doesn't read run over in-memory pipes** of 8 bytes each way (axum serves any `Listener`), since the server's few small frames never fill TCP's buffers. The auth harness's session reads can fail, hang (and say when they do) or queue behind the write connection, each only `SessionReads::find`; the token service reads through a copy of the hooked store that shares those switches and has write queues of its own.

*Decided by the review agents, approved by the user at the plan review:*
- **S38 (security). The commit count's mark is a per-commit generation** (PR #66's follow-up). sqlx 0.9's `Transaction::commit` drops its connection inside its last poll, which spawns the connection's return; another tokio worker can then settle commit A, release the one write connection and let commit B begin and take its turn, all before A's thread runs `returned()` (an OS preemption, or tokio's LIFO slot off). A's late return then cleared B's mark, and a B dropped mid-`COMMIT` never got its settling move. `CommitCount` keeps the last generation handed out and the generation of the commit whose `COMMIT` hasn't returned (0 when none): a turn takes the next generation, its return clears the mark only with a compare-and-swap on its own, and the release hook takes whatever mark stands, pinging and moving the count when there was one.
  - *Rejected:* the shared flag (it rests on tokio's scheduling); clearing the mark before the connection drops (a `COMMIT` sent by hand, against sqlx's transaction); clearing it only in the hook (every commit would move the count twice).
- **S39 (security). The write pool has no lifetime** (PR #66's follow-up, the user's instruction; the agent chose between its two options). sqlx closes a returned connection past its lifetime (30 minutes by default), or one returned to a closed pool, without running `after_release`. `.max_lifetime(None)` on the write pool removes the first case; the second can't matter, since serve stops every socket within the drain before `database.close()`, and the read pool closes first. The idle timeout and the check before an acquire close only connections that sit unused, which are always settled. ADR-0015's "otherwise sqlx's pool defaults" is amended.
  - *Rejected:* also moving the count once the write pool's close returned (no socket can observe that path, and its test couldn't be red first); a lifetime kept as a test setting (the cause would stay in production code).
- **S40 (security, low). A flood on a hidden bot is an accepted risk, and tested** *(amended at PR #67's review, and in group E's first commit)*. A socket lags only while one of its branch bodies runs (a send of up to 10 s, a session check, a rights rebuild, a bot's or a mode's read) and more than 1024 events are published meanwhile; filtering a hidden event is a lookup, on rights as new as every commit counted: on the first wake after a commit, hidden events wait, unjudged, behind that one rights rebuild, and a rebuild that fails there closes the socket with 1013 (R47). The ingest publishes up to 1000 stored lines at once, against a bus of 1024, and nothing counts an agent's reports per stream (the accepted "an agent's reports about its own bots are trusted"). What leaks is at most one bit per 5 s (S35's gap; R19's `resync` has no count): that more than 1024 events were published somewhere, never which bot, kind or how many.
  - *Rejected:* coalescing at the source (breaks "everything else at once", and can't touch chat); a filtered queue per socket (against S35's "the receiver is the queue", and not cheap); separate buses (they move the threshold and break the ordering of a line before its outcome); a larger bus (it bounds nothing).

- **S41 (security). *Decided by the review agents, approved by the user at the plan review:*
- **S44 (security, low). `PRAGMA secure_delete = ON` on every connection,** beside `trusted_schema` in the connection options' shared part. Age retention deletes in ID order: each batch of 1000 typical rows empties about 55 table leaf pages and 9 `at` index pages, about 98 % of its text, and SQLite reuses freed pages last in, first out, so a large delete's pages can keep their text for good. FAST overwrites only within pages that stay in use, never a freed page. ON costs about 64 extra page writes per batch (about 0.5 MiB of WAL, twice that with the checkpoint): about 6 KiB a second at a realistic 10 lines a second, about 1 MiB a second at the ingest's ceiling; nothing fsyncs at commit (WAL, `synchronous = NORMAL`), so the write connection is held about as long. libsqlite3-sys 0.37.0 bundles SQLite 3.51.3 without `SQLITE_SECURE_DELETE`, so it was off; the read pool can't delete (`query_only`) but gets it too, so every connection holds it and one test shape pins both. *What lingers:* a freed page's old image in the WAL until the next checkpoint (or the server's stop, whose close checkpoints), whatever the disk keeps below SQLite, and backups for their own retention (P12.3); the runbook advises encrypting the host's disk. As a side effect, a re-sealed vault envelope that changed size leaves no old bytes inside its page.

*Decided by the review agents, approved by the user at the plan review:*
- **S61 (security, low: availability). A stopped watch never starts a new one.** The live layer starts a watch only on explicit triggers, only while signed in: sign-in (once per generation, remembered by the runtime's layer, so StrictMode's second effect or a hot reload starts nothing), R73 (the runtime's `recovered()` while the current generation's last watch ended with `certificate`), and the profile save's `change: "none"` answer after `cancelLogout()`. An `Ok` of the current watch leaves the layer idle with no hint; any other watch's is ignored. In Rust the stop comes after `health_live` and just before `write()`, so a refused save leaves the watch running, and the switch's refusal of new watches ends before its write guard is released. *Why:* an `Ok` doesn't say why it stopped, and each new watch connects at once with its backoff at zero, so a restart on `Ok` would bypass S54; two attached layers would replace each other forever, each minting a ticket per round. *Rejected:* restarting at once (the identical save stops the watch during `logging_out`: never restarting, or spinning until the switch answers); bounded restarts (the same flaws within the bound, and a "stopped" text with no error). *Later:* a Rust-side stop that keeps the session (an updater, a suspend) brings its own UI trigger.
- **S62 (security, low). G2 drops the updates of a watch that isn't its current one** (H's note, built in G2). The layer numbers each watch and records its generation; the current watch is the newest of the current generation while the session isn't signed out (a `logging_out` save keeps it current). Starting a watch drops every hold and clears the hint; a non-current watch's updates and settling change nothing. *Why:* `recv` can hand out an update queued before a stop, and Tauri orders messages only within one channel, so a late frame could be held and replayed over a fresh refetch, a late disconnect would show the hint while live, and a hold could cross into the next sign-in's cache. *Rejected:* applying everything until H; dropping by generation only.
- **S63 (security, low). A failed fetch applies its held events to the data it keeps,** in order, data-only: the query keeps its error and its stale mark (a `setQueryData` would record a success and erase the error a failed "Show more" or the account's 404 must show), and events after the failure until a fetch succeeds are written the same way. No read follows. A cancellation carries the hold into the fetch that replaced it; a removed query takes its hold with it. *Why:* the held events are the only record of what changed since the kept data was read; applying them leaves the cache where it would be had the fetch never started, and ADR-0017's "no retries" stays. *Rejected:* dropping them (a lost `bot_removed` keeps a revoked bot on screen); holding until the next success (it freezes the query and reorders events); drop and invalidate (an automatic retry).
- **S64 (security, low: DoS and resources). A failed `Channel::send` stops the watch:** `LiveEvents::close` while the read guard is still held, then `Ok`, as a stopped watch, with no log line. *Why:* in tauri 2.12.3 the types can't fail to serialize and a closed or reloaded page isn't an error; the one real failure (the event loop gone, or Windows' message queue full) breaks the channel for good, since Tauri numbers each message before its eval and the page delivers in order. *Rejected:* a rejection code (none fits, a new one is beyond S59); ignoring it; stopping after N failures.
- **S65 (security, low). The waiting list from a `bot` frame,** only when `["accounts","awaiting"]` holds data: pending and listed, replaced; pending and not listed, invalidated; `active`, `reauth_required` or `refused`, removed if listed; a status this version doesn't know, invalidated. *Why:* only the server decides who reviews a link (`authorize(ReviewLink)`, ADR-0018 S5): an Admin's own pending link reaches their socket but isn't theirs to review. *Rejected:* placing it by ID (a client copy of `authorize()`); leaving the list.

## Consequences
- **Easier:**
  - A refused login can't be undone by the next backoff: the server's grant after it is always fresh.
  - A user learns at once that a Minecraft server won't take a command, instead of a success the server dropped.
  - One chat rate per bot, set in one place, holds on both ends.
- **Harder:**
  - The protocol gains two fields before its first release (`Backoff.fresh`, `BotSpec.chat_rate`); after the release, removing either needs a version decision (S9).
  - fleet-mc reads another server packet, the command tree, as untrusted input.
