# 0019. The control plane: conventions, Phase 10 refinements

- **Status:** Accepted
- **Date:** 2026-10-15; groups B and C 2026-10-16; groups E and F 2026-10-17
- **Related:** Plan.md Phase 10 (P10.1–P10.10), P11.1, P11.2, P11.3, P11.4, P11.9, P12.1, P12.2, P12.4, P12.6, P13.1, P13.2, P13.4, P13.5, P13.6, §4, §5, §6, §7.2, §7.4, §7.5, Appendices A to D; ADR-0002, ADR-0010, ADR-0011, ADR-0013, ADR-0014, ADR-0015, ADR-0016, ADR-0018

## Context
Phase 10 connects agents to the server: enrollment with a server-signed certificate, one gRPC stream per agent over mutual TLS, the scheduler and the reconciler, short-lived session grants, the agent's client and the server's batched ingest. The stream crosses the project's sharpest trust boundary after the public API. An agent host is one of the attackers in the threat model, and the server hands that stream the only Minecraft tokens that ever leave it.

Before any code, the plan found one conflict between the user's phases: P10.5, P10.6 and P10.8 need P11.1's `bots` table (and `chat_messages`), and Phase 10's DoD ("pressing Start in the app brings a bot … Online") needs P11.2's start endpoint and P11.9's screens. The user decided it (U1). Every other open question went to its own read-only review subagent, given the options neutrally (CLAUDE.md's step 10). The user approved their decisions (S1–S9) at the plan review and added two notes for later groups. Each later group asks its own questions in its session and adds its decisions here.

### Decided by the review agents *(approved by the user at the plan review)*
- **S1 (security). Certificate renewal stays in P13.6,** which already plans it ("renew at 2/3 of the lifetime"), with P12.6's runbook. Group A leaves `RenewCertificate` out of the proto: a new RPC later breaks no agent. Phase 10 only keeps the way open: `agent_certs.agent_id` is indexed but not unique (B); the SAN's agent ID comes from the server's record (B); the agent writes its key and certificate atomically, owner-only, on its `/data` volume (B); a connection needs a fingerprint that's neither revoked nor expired (C); disable revokes every fingerprint, and `GET /agents` shows `not_after` (P10.10); an expired certificate joins P10.9's rejections. *Why:* it's the user's recorded plan; building renewal next to P13's threat-model review is safer than adding the path a stolen key would use to the biggest phase; a unique `agent_id` now would force a table rebuild then. *Rejected:* building it in Phase 10 (overturns P13.6), dropping it (Owner-only re-enrollment every 60 days per agent).
- **S2. The validated messages live in fleet-proto,** in `fleet_proto::control`, next to `generated` and never inside it: one `AgentMessage` and one `ServerMessage` built from core types, each read with `TryFrom` from its generated envelope and written back the same way. Agent and server never match on generated oneofs. What exists only on the wire stays in fleet-proto; what is stored, shown or used by a policy goes to core. *Why:* it mirrors the HTTP side, where fleet-api-types holds the DTOs and the server's services see core types; core stays the pure domain; P13.2 gets two fuzz targets that reach every conversion. *Rejected:* protocol enums in core (transport types in the domain, a second chat-failure enum there); matching on generated types in both binaries (validation repeated, unfuzzable).
- **S3 (security). Correlation.**
  - **`SendChat`** carries a new core ID, `ChatRequestId` (v7), which the server's chat service mints through `Clock` and `SecureRandom` (P11.3); `ChatSent` and `ChatFailed` repeat it, and the agent maps it to the runtime's `ChatTicket`. *Not a u64 counter:* an outcome buffered across a server restart would meet the restarted counter. *Not the HTTP `RequestId`:* it names one HTTP request, never an entity (ADR-0015).
  - **`SessionRequest`** carries the agent's own number (`SessionRequestId`, a `NonZeroU64` counted from 1 per process), which `SessionGrant` and `SessionDenied` repeat with the bot. The agent drops an answer it no longer waits for. *Not the bot alone:* the server may take 2 minutes, the agent waits 30 s, and a late grant from before a rejection could answer the next `fresh` request.
  - **`SessionRequest` names no account:** the server takes it from its own assignment, so "an agent gets tokens only for its own bots" stays the server's decision.
  - **Restart, reset and resume** get a message with P11.2 (E), as a new oneof case, together with P11.2's own questions about them.
- **S4 (security). A mode crosses the wire as structured messages** that mirror `ModeDefinition`: `Step { action, schedule, probability }`, a oneof of the ten actions, a oneof of the two schedules. Reading rebuilds a `ModeDraft` and runs `ModeDraft::validate`; a step whose action or schedule this version doesn't know is refused. *Why:* JSON stays the stored format alone (ADR-0010), so a database migration that rewrites stored modes can't change the protocol; serde_json's errors quote their input, and fleet-proto's never do. *Rejected:* the JSON form in a string (a third JSON use, migrations coupled to the wire, quoting errors on the agent); `google.protobuf.Struct`.
- **S5 (security). Times and IDs.** Times are `optional int64` milliseconds since the Unix epoch (`*_unix_ms`): reading refuses a missing one and one outside 0000-01-01T00:00:00.000Z to 9999-12-31T23:59:59.999Z, the database's and the API's range; writing drops anything finer than a millisecond and refuses a time outside the range. IDs are 16 bytes: a bot's, an account's, an agent's and a chat request's must be v7, a Minecraft profile's non-nil. No well-known types, so prost-types stays build-only. A heartbeat carries no time: the server stamps `last_seen_at` with its own clock. *Why:* every value round-trips exactly, with no text parser facing untrusted input; whatever an agent sends, the server can store. *Rejected:* string times and IDs (canonical-form checks, a third time parser, twice the size); `google.protobuf.Timestamp` (a run-time dependency, nanos to check).
- **S6 (security). Text from Minecraft is cleaned again; validated values are strict.** Received chat and a kick's key and message are rebuilt through `IncomingChat::from_parts` and `DisconnectReason::kicked`, which clean and cap them; only structural faults are errors. `truncated` is the agent's flag OR the server's own cut. Validated values are refused, never repaired, in both directions: a chat message must arrive trimmed, a server address in its written form, conflict texts, names and versions as their constructors accept them (a set's order and duplicates are accepted). *Why:* a compromised agent gains nothing from dirty text it can't store, while a stricter rule would drop an older agent's report (a duplicate-login Paused kick) whenever the sanitizer's lists grow; repairing a human's text silently changes it (ADR-0013). *Rejected:* refusing text that cleaning would change; counting cleaned messages inside the conversion (it can come at ingest).
- **S7 (security). Secrets stay out of `Debug`.** The build script skips prost's derived `Debug` for each message that holds a secret (`OnlineSession` now, `EnrollRequest` in B), listed in its `REDACTED`. `fleet_proto::redact` writes their `Debug`, which names only what isn't sensitive and ends with `..`, and a `Drop` that wipes the secret. The conversion moves the token out with `mem::take` into `SecretString::from(&str)`, which allocates exactly its length, and wipes the original. The enclosing oneof's and envelope's derived `Debug` call the hand-written one, so forgetting it fails to compile; `missing_debug_implementations` stays out of the generated module's allowances. A test fails on any field named like a secret (`token`, `secret`, `password`, `key`) outside a redacted message, unless it's on a not-secret list with a reason (a kick's translation `key`). *Accepted residual:* the buffers tonic, h2 and rustls decode and encode into can't be wiped, as ADR-0018 accepted for hyper's. *Rejected:* no `Debug` at all (it spreads to every type that holds a message, and would need the allowance loosened); convention only (prost's derive prints the token); a wrapper message; hand-written wire code.
- **S8 (security). No agent labels in v1,** in no config key, proto field, core type or column: nothing schedules by them through Phase 13. **Capacity** is the agent's `[runtime] max_bots`, sent in the hello as the new core `AgentCapacity` (1–1000, the config's range); 0 or above 1000 is refused, never clamped. Free capacity also counts the bots unassigned whose `Removed` hasn't arrived. *Why:* capacity decides which agent gets which bots, and so which session tokens; labels can come later as an additive field. The threat model records that only Owner-only enrollment, mTLS and revocation stop an agent inflating its capacity. *Rejected:* labels now (six layers without a consumer); a bare proto field (unvalidated input).
- **S9 (security, low). "The proto codegen check"** (P0's promise in CLAUDE.md's commands table and the justfile) is a pinned wire-schema snapshot. build.rs generates the code into `OUT_DIR`, as P10.1 says, and renders the compiled descriptor as text: every message's fields with number, name, label, type and oneof, reserved numbers and names, every enum, the service with its streaming flags, and the redacted messages, without comments or source positions. `tests/protocol/schema.rs` snapshots it under `PROTOCOL_VERSION`, so a wire change shows in review; no recipe or CI job is added. The protocol stays at version 1 until the first release (P12); after that, a snapshot change needs a decision about the version. *Rejected:* committing generated code with a freshness check (contradicts P10.1's build script, churns on every prost bump); dropping the promise.

### As built (group A)
- **The crate** `fleet-proto` (depends only on fleet-core): `proto/fleet/v1/{agent,bot,chat,mode,common}.proto`, package `fleet.v1`, with the `AgentControl` service and its `Connect` stream; `build.rs`; `src/{lib.rs, control/, convert/, error.rs, redact.rs}`. The files live under `crates/`, the only folder the agent image's `.dockerignore` admits. It joins `stable_crates`.
- **The build:** `protox::compile`, then `tonic_prost_build::configure()` with client and server, `build_transport(false)`, `skip_debug` for `REDACTED`, and `compile_fds`. The schema is rendered through protox's re-export of prost-reflect, so the build needs no other crate. `main` returns a `Result`.
- **`fleet_proto::generated`** carries `#[allow(clippy::pedantic)]` and nothing else: the generated code trips only pedantic lints (`doc_markdown`, `must_use_candidate`, `default_trait_access`, `missing_errors_doc`), none of the workspace's denied ones.
- **`fleet_proto::control`:** `AgentMessage` (`Hello`, `Heartbeat`, `Status(BotSnapshot)`, `Event(BotEvent)`, `SessionRequest`), `BotEventKind`, `ChatFailedReason` (the runtime's five delivery failures and six refusals), `SessionRequestId`; `ServerMessage` (`Welcome`, `Reconcile(Vec<Assignment>)`, `Assign`, `Unassign`, `Update`, `SendChat`, `SessionGrant`, `SessionDenied`, `Reject(RejectReason)`); `MAX_BOTS` (1000, pinned equal to `AgentCapacity::MAX`). `Welcome`'s heartbeat interval is 1 s–5 min on the wire.
- **The leaf conversions** are trait impls between core's and the generated types: `BotSpec`, `ModeDefinition`, `StickyState`, `BotNotification`, `DisconnectReason` and `IncomingChat` are written with `From`; `BotState` and `BotSnapshot` with `TryFrom`, since they hold times. `SessionCredentials` converts inside `SessionGrant`.
- **Errors:** `ConvertError { field, index, problem }`, where `field` is `Message.field` in the protocol's names, `index` the position in the innermost list (a bot in a hello or a reconcile, a mode's step), and `Problem` one of `Missing`, `Unknown`, `WrongLength`, `NotV7`, `Nil`, `OutOfRange`, `TooMany`, `Duplicate`, `NotExact`, `InvalidToken` or a wrapped core error, none of which carries input.
- **fleet-core:** `id::ChatRequestId`; `value::AgentCapacity` (`NonZeroU16`, `TryFrom<u32>`) and `value::AgentVersion` (1–64 of `[0-9A-Za-z.+-]`, starting with a letter or digit, like `AgentName`).
- **Tests,** each red first against compiling stubs with the real signatures:
  - **fleet-core:** 29 for the two values, 19 of them red against stubs that refused everything; the others check refusals and the errors' fixed texts. The capacity property passed at first, since uniform `u32`s almost never land in 1–1000; its input is weighted toward the range now, and it went red. `ChatRequestId` is one more instance of the ID macro, covered by the two tests that list every ID type.
  - **fleet-proto:** `tests/protocol/` (round trips, decoding any input, one case per rejection, redaction, the schema) and unit tests of the helpers. 147 of 164 failed against stubs that refused every read and wrote default messages. The 17 that passed checked what a stub happened to answer (an expected `Missing`, the helper `required`, the constant pin, the error's formatting) or held vacuously while everything was refused (the decode properties, the guard).
  - **Temporary mutations** showed those red, each reverted and checked by checksum: the agent's `truncated` flag dropped (the clean-text property), a probability wrapped instead of refused (the mode property), the heartbeat read without its range (any server bytes), an unspecified enum read as unknown and a missing value read as unknown (seven rejection cases), the error without its position, a refused token named in the error, a field named `password` outside a redacted message (the guard), and a time read without its range (the time property and its unit test).
  - **Found by a mutation:** an encoder that swapped `AgentBusy` for `ShuttingDown` passed every property, since random cases reach one reason of eleven in one event kind of seven too rarely. Five exhaustive tables now cover every value of each mapped enum, and swaps in three of them went red. The time property's input is weighted toward the range's edges too: uniform `i64`s rarely land in chrono's range outside years 0–9999.
  - **The snapshot** `protocol__schema__wire_schema.snap` was read before it was accepted.
- **Found during the build:**
  - The zeroizing `Drop` forbids struct-update syntax on `OnlineSession`, so its test cases change a valid session through a helper.
  - Integration tests read `OUT_DIR`, so the schema test and the guard read the build script's rendering directly.
  - chrono without features has no `to_rfc3339`; the range test compares the date's parts.

### Group B: decided by the review agents *(approved by the user at the plan review)*
- **S10 (security). Every key is Ed25519 from getrandom bytes:** the CA's, the server's, the agent's, and the only key a CSR may carry. 32 bytes from the `SecureRandom` port (getrandom on the agent) are wrapped as PKCS#8 v1 (RFC 8410's fixed prefix) and loaded with `PKCS_ED25519`; `KeyPair::generate*` is never used, since it draws from aws-lc's own RNG. *Rejected:* rcgen's generator (an exception to rule 4 and the port); P-256 alongside (a second key type for no gain).
- **S11 (security). The profiles:** a 16-byte serial from `SecureRandom` (first byte 0x40–0x7F); validity from an hour before the clock's time to the lifetime, in whole seconds, within 1970–9999. The CA (`afkfleet CA`, ten years, path length 0, keyCertSign), the server (`afkfleet server`, one year, serverAuth, 1–8 names from `--dns`/`--ip`), agents (`afkfleet agent`, `[grpc] agent_cert_lifetime_days`, clientAuth, one SAN `urn:uuid:<agent ID>` from the server's record). `pki server-cert` renews the server pair from the same CA.
- **S12 (security). `pki init` and serve's reading:** the four `[grpc]` files only; every problem checked first; `create_new` temp files (0600 on Unix), synced, published with `hard_link`, which never replaces; a failure removes only this run's names. Serve reads the four through `secret_file` before the runtime and refuses a missing file (with `pki init`'s name), more than one certificate or key, a CA certificate that isn't a CA's, a key that isn't its certificate's, and a server certificate the CA didn't sign; an expired server certificate is an `error`, and serve runs on. `just dev-server` creates the dev PKI once.
- **S13 (security). One gRPC port** on `[grpc] bind` (127.0.0.1:7443 by default), only while `[grpc]` is configured: TLS with the server certificate, the CA as the root for client certificates, which are optional, but verified when presented. B serves `AgentEnrollment`; C adds `AgentControl` behind a gate that refuses a call without a verified client certificate. No compose change in B.
- **S14 (security). Enroll's limits and answers:** 8 KiB decoded, 16 KiB encoded (tonic's own `OUT_OF_RANGE` above), no compression; a CSR of 1–4096 bytes; 15 s in the handler, below the agent's 20 s; a 10 s handshake, 16 calls per connection, connections of at most 60 s plus 20 s. `[rate_limits] enroll_per_ip_per_min` (1–60, 5) is spent first, keyed like the HTTP limits (an IPv6 client by its /64). Every answer carries `x-request-id`; each case has one fixed message (the table in `grpc::enrollment`). Logs never hold the token, its hash, the CSR or the peer's address.
- **S15 (security). The bundle:** one line, `<token>.<CA fingerprint>`, 146 characters; the agent reads it from stdin only (a terminal refused, at most 1 KiB, wiped), checks `[control_plane] ca_cert_file` against the pin before any connection, and trusts that one certificate as tonic's only root. A wrong CA file shows both fingerprints and sends nothing.
- **S16 (security). A token stands for one new agent:** Owner-only, step-up, no body, 15 minutes, at most 20 pending, no list or revoke in B. The agent's name comes from its own config, unique ignoring case among enabled agents; every Enroll creates a new agent with a server-minted ID; no token re-issues an identity. Signing runs in `spawn_blocking` before one write transaction that checks the token again, stores the agent and its certificate's fingerprint, and uses the token conditionally; a certificate that loses a race is dropped unsent. The answer carries no CA certificate.
- **S17 (security). What's audited:** `enrollment_token.create` (the Owner and the IP over HTTP; no actor from the host; `expires_at`, `via`); a successful Enroll commits `agent.enroll` (no actor, the peer's IP, the agent, its fingerprint, `not_after`, name and token ID) and `enrollment_token.use`; a real token that's expired, used or whose creator lost the right is an `agent.enroll` Failure with its reason, at most 10 per token. Unknown and malformed tokens, refused CSRs and rate-limited calls aren't audited.
- **S18 (security). An identity that exists is refused, never replaced:** nothing may be at `key_file` or `cert_file` (a file, a folder, a dangling link) and no `<file>.tmp` lock; the folders must exist. The key is written into its temp file before the call; afterwards both are linked with `hard_link`. A failure after the server answered is exit 3, naming the agent to disable.
- **S19. The agent's command:** `afkfleet-agent enroll --config PATH`, the same `config::load` as `run`, `[control_plane]` required. `url` is `https://host:port` (no credentials, path or query, a port other than 0) and the three files absolute and distinct, for `run` too; `run` keeps refusing `[control_plane]` until P10.7, pointing to `enroll`. Timeouts: 5 s to connect, 5 s for the handshake, 20 s for the call, 30 s in all; the answer at most 16 KiB; no retry. Fixed texts per failure, never the server's message.
- **S20 (security). Windows:** the agent's and `pki init`'s files inherit their folder's permissions there, since std gives them no owner-only mode; both commands say so on Windows, and the README and the threat model record it. No ACL crate and no `unsafe`.
- **S21 (security). The order of Enroll's checks** (a tie-break agent, with both rationales): the peer's address, the rate limit (both in the gate), the conversion, the token, the name, the CSR, the transaction. The token comes before the CSR, so x509-parser, signatures, blocking threads and the CA key stay away from anyone without a token; the name comes after the token, so names can't be probed without one. *Accepted:* a token holder can probe agent names, as an invitee can probe usernames (ADR-0016). *Rejected:* S14's first answer, the token last, which puts the parser in front of the internet.

### Group B: reconciliations *(for the user's review)*
- **R1.** `enrollment_tokens.created_by` is NULL for the host's tokens; the creator's re-check applies only when there is one; the cap of 20 counts every pending token.
- **R2.** Without `[grpc]` the token route answers 404, after the step-up check, as `POST /accounts/offline` does while it's off; the host command refuses with "the control plane is off".
- **R3.** `enroll`'s exit codes are 0, 1, 2 and 3 (S18's case).
- **R4.** The dev agent dials `https://127.0.0.1:7443`, and the dev server certificate names `localhost`, `127.0.0.1` and `::1`.
- **R5.** `pki server-cert` never overwrites either.
- **R6.** Ed25519 only (S10 over S14's P-256).
- **R7.** The token route answers `{id, bundle, ca_fingerprint, expires_at}`.
- **R8.** The agent's timeouts and its answer cap are S14's shared constants.
- **R9.** `max_connection_age` bounds every connection while `Enroll` is the port's only service; C replaces it with a bound for connections without a client certificate, or records the residual. As built (PR #49 review): with the grace set, tonic 0.14.6 sends no GOAWAY at 60 s but cuts the connection, calls in flight included, at 80 s; removing the grace isn't a fix either, since tonic then polls the finished timeout future again.
- **R10 (security), decided by a review agent during the build.** `EnrollResponse` carries the certificate as `string certificate_pem` instead of `bytes certificate_der`. rcgen 0.14 can't PEM-encode a certificate it didn't make, and the agent has no `base64`; the server holds rcgen's PEM of the same DER it fingerprints and stores. The agent stores the text it received only after checking it: exactly one PEM section, a certificate, with nothing outside its `BEGIN` and `END` lines; a client certificate the pinned CA signed, valid now (rustls's client verifier, the check C's port makes); and its own key. *Rejected:* a DER file (pushes the same choice to P10.7, after the wire is merged); `base64` in the agent (needs the user's approval when a rule-respecting option exists); a hand-written encoder (works around the registry); both forms on the wire (two copies that could disagree). Cheap to change until the first release.

### Group C: decided by the review agents *(approved by the user at the plan review)*
One read-only agent per question, each given the options neutrally; they read CLAUDE.md, Phase 10, this ADR and the threat model in full, then the code.
- **S22 (security). The connection bound (R9).** The listener wraps every accepted socket in its own `Bounded` IO before tonic's TLS, and cuts it at 80 s (S14's effective value) unless a `Lift` is held. A Connect stream takes the lift after its identity, its hello and its registration, before its slot is activated and Welcome queued, so the age can't cut the connection between the two, and drops it when it ends, so the 80 s start again then *(worded as built after PR #50's review; it said after Welcome)*. tonic's `max_connection_age` and its grace go. The connection's info is the listener's own `Connection` (the peer's address and the bound's handle), read as `TlsConnectInfo<Connection>`; Enroll's gate takes the peer from it. *Why:* no crate, S13's one port, and a revoked or never-welcomed certificate can't hold a connection either. *Rejected:* any verified certificate lifting the bound (a revoked key would hold connections forever), an own TLS acceptor (a crate, and the same flaw), no bound (a slow-body Enroll unbounded), a second port (overturns S13). *Residuals:* an admitted agent's connection can carry up to 15 more calls with no age; connections per address aren't counted.
- **S23 (security). Liveness.** HTTP/2 keepalive on both ends, no proto change. `[grpc] heartbeat_interval_secs` (1–60, 10) and `heartbeat_timeout_secs` (2–300, 30, at least twice the interval) build a validated `Heartbeats`; the server's keepalive pings every interval and closes a connection whose ping isn't answered by the timeout (hyper's server pings idle connections too). Every agent message that converts resets the stream's deadline. *Rejected:* a server heartbeat message (a proto change; it can't close a silent TCP connection, and it queues behind a reconcile), both. *Later:* G's channel keeps alive every 10 s with a 20 s timeout, while idle too, and beats on Welcome's interval.
- **S24 (security). The handshake and its answers.** The gate checks the certificate first, then mints the request ID, then spends the limit (S30). Before the stream opens: the fingerprint's row, then revoked, expired (`now >= not_after` by the server's clock), disabled, and only then the SAN (exactly one `urn:uuid:` of the row's agent); all five failures are one `UNAUTHENTICATED`. After it opens (`x-request-id` in its headers): the first message within 10 s (`HELLO_TIMEOUT`; the agent waits 30 s, `WELCOME_TIMEOUT`), read by `fleet_proto::control::read_hello` (a hello at all, then `protocol_version` equal to `PROTOCOL_VERSION`, 0 included, then the conversion), then the name, byte for byte. `Welcome` gains the agent's ID. A second hello ends the stream; after a Reject the stream ends OK. One fixed message per case; the hello's name, the peer and certificate bytes are never logged. *Why:* nothing is parsed for anyone unauthenticated, identity answers are uniform as enrollment's are, and exact equality fails safe. *Rejected:* a version range, a server version in Welcome, case-insensitive names, a reason per identity failure.
- **S25 (security). Sizes and queues.** `fleet_proto::control::MAX_AGENT_MESSAGE_BYTES` 8 MiB (the largest legitimate hello is 4.09 MiB: 1000 snapshots with kicks at their caps) and `MAX_SERVER_MESSAGE_BYTES` 128 MiB (the largest reconcile is 65.3 MiB, its conflict texts at their cap), for both ends. `fleet_proto::codec::BoundedCodec` (build.rs's `codec_path`, outside `generated`) counts a hello's running bots through a decode-only view of zero-sized entries and refuses more than 1000 before prost builds them: an empty entry is 2 bytes on the wire and about 112 in memory. Each stream's outbound queue holds 2048; a send never waits: over the limit is `TooLarge` (the stream stays), a full queue is `QueueFull` and ends the stream, so the agent resyncs. No rate limit on what an agent sends. *Rejected:* tonic's defaults (a 4 MiB decode limit refuses a legitimate hello), the amplification as an accepted risk, chunked hellos (a protocol change).
- **S26 (security). One stream per agent: a second is refused.** A second Connect while the agent's stream lives gets `Reject(AlreadyConnected)` after its hello checks; the live stream is untouched, and the slot frees only when its session task has ended. A message on the live stream after a refusal proves two holders of one identity: an `error` line and `security.agent_identity_conflict`, at most once an hour per agent. *Rejected:* replacing (a thief could push the real agent out, and two processes would kick each other's accounts), replacing after silence, a per-process ID.
- **S27 (security). A permission that ends mid-stream.** A per-stream timer ends the stream at its certificate's `not_after`, and a 5 s sweep (one query for every admissible fingerprint) ends any stream whose certificate is revoked or expired or whose agent is disabled; each ends with `Reject(AgentDisabled | CertificateRevoked | CertificateExpired)` ahead of anything queued, and nothing queued goes out after it. A disabled agent's stream ends `AgentDisabled` whatever its certificates' state. The disable service commits, then ends the stream. *Rejected:* a stream living on past its permission, a grace, refusing a host disable while serve runs (it can't be detected).
- **S28 (security). Reports about bots.** The registry keeps, per agent, the bots it holds (`Assigned` or `Releasing`), empty until D fills it. One function admits every message: a status or an event for a bot it doesn't hold is dropped, counted and logged at `debug`, and the stream stays; a releasing bot passes only its `Removed`, which ends the hold; every session request in C gets `SessionDenied` with `retryable` true (false would fail the bot for good). A hello's bots that aren't held are ignored. Housekeeping logs one line per agent with refusals. *Rejected:* ending the stream (honest races exist, and it amplifies a hostile agent), refusing the hello.
- **S29 (security). Presence.** Nothing is written per message. An accepted hello: one transaction checks the certificate and the agent again, writes the capacity, the version and `last_seen_at` (never backwards) and commits `agent.connect` before Welcome; if it fails, the hello is refused as busy. The stream's end writes the last message's time and `agent.disconnect` with its reason. *Rejected:* memory only (the columns would stay empty), unaudited writes and a periodic flush (new exemptions).
- **S30 (security). Connect's limit, and which refusals are audited.** `[rate_limits] connect_per_cert_per_min` (1–60, 10), keyed by the presented certificate's fingerprint, spent in the gate before any parse or read. A known certificate's identity refusals (`revoked`, `expired`, `disabled`, `san_mismatch`, `name_mismatch`) are `agent.connect` Failures, at most 10 per agent in a rolling 24 hours; an unknown certificate is an `error` line, never audited. *Rejected:* no limit (security rule 3), a limit per address (agents behind one NAT), a permanent cap (one episode would hide a later theft).
- **S31. The agents' API and the host commands.** `GET /agents` pages like every list and shows every agent: `{id, name, enabled, status, capacity, version, connected_since, last_seen_at, not_after, created_at}`, the status `online`, `offline`, `expired` or `disabled` (an `Open<…>`), `not_after` the latest of the unrevoked certificates. `POST /agents/{id}/disable` (step-up) answers 200 with the agent, the same with no entry when it's disabled already, and works with `[grpc]` off; `agent.disable` records the name, the certificates revoked and `via`. The host gets `agent list` and `agent disable --id`. fleet-client's agents methods come with P11.9.

### Group D: decided by the review agents *(approved by the user at the plan review)*
One read-only agent per question, each given the options neutrally; S43–S45 closed gaps the design pass found.
- **S32 (security). No time ever moves a bot.** A stale or disabled agent's bots keep `agent_id` and read Unknown; they leave only by that agent's `Removed` of a bot the server released (S44), a hello of its that doesn't list them, or `afkfleet-server agent release --id`, which only a disabled agent's bots may take (one transaction clears its bots and its release records; P11.9 adds the API action). ADR-0013's "(or a timeout)" is dropped: no timeout proves anything (a joined bot needs no token; an unreachable agent keeps its bots, §6 row 9). A release proves the old agent can never join or rejoin the bot (revoked certificates, no stream, no assignment, no grant); it can't prove that a session joined before the disable isn't still alive on a partitioned host. The operator vouches for that, and the command's help says so; if they're wrong, the new login kicks the old session once, which Pauses and can't come back. *Rejected:* moving at the disable (a partitioned agent never gets the Reject), any timeout. *(Worded after group F's S63, approved at F's plan review: "no grant, and none kept once its process ended"; an agent host that's only cut off may also rejoin its disconnected bots with the sessions it kept, until they expire, and the operator vouches for that too.)*
- **S33 (security). Which bots are placed:** one fleet-core predicate (`placement::placeable`): a server address, desired Running, an enabled owner, and an active Microsoft account or an offline one while `allow_offline` is on; otherwise an `Unplaced` reason. A placed bot that stops qualifying gets `UpdateSpec(Stopped)` first and `Unassign` after a resting report (Stopped, Paused, Failed) or a 60 s bound, so a Paused report can't be dropped as a releasing bot's status (S28) and the next agent kick a human (ADR-0013, P4.7). A deleted bot gets `Unassign` at once. A stopped bot holds no slot; a sticky bot stays placed while it qualifies. *Rejected:* placing `reauth_required` bots, keeping stopped bots placed.
- **S34. `auto_start`:** the scheduler and the reconciler never read it, and D's migration leaves the column out; it arrives with its first writer, E's `PATCH`. What auto-start does for users is the user's (taste), asked before E.
- **S35. Bot IDs:** a new bot's ID is minted right after its account's, from the same `now`. The backfill gives each existing account's bot the account's ID with the high bit of the last hex digit flipped: random bits only, so still v7, distinct from the account's and every other bot's, and deterministic, so the test checks exact values. *Rejected:* the account's ID itself (two entities, one value), SQL randomness (`randomblob` isn't getrandom).
- **S36 (security). Every change of a bot's agent is its own short transaction with its own audit entry,** no actor: `bot.assign {agent}`, `bot.unassign {agent, reason}`, `bot.detach {agent, reason}` (`removed`, `not_running`, `agent_released`), committed before the registry and the message. Unchanged assignments write nothing. *Rejected:* one entry per pass (metadata can't name 1000 bots), a `commit_unaudited` exemption.
- **S37 (security). The reconciler:** a full pass at startup and every 30 s, and one on a hint. One task owned by serve's `JoinSet`, fed by a bounded queue of hints that callers `try_send` (a full queue forces one full pass and logs one `warn`). Facts live in state (the registry's live streams and their holds, the latest reports, the released notes; the database), so a lost hint costs latency only. The decisions are a pure fleet-core planner (`placement::plan`); the database is reached through `ports::assignments`, implemented in `app/agents/`. *Rejected:* events only (no recovery from a missed one or the host's own writes), a periodic pass alone (slow starts), callers running passes under a lock (callers wait).
- **S38 (security). `modes`:** `visibility` CHECKed (`private`, `shared`), the built-ins `shared` (a CHECK: an owner or shared); no index on `name` yet (P11.4's); `version >= 1`, `created_at`, `updated_at >= created_at`; `definition_json` CHECKed as a JSON object. The seeds `afk` and `farm` have fixed IDs `01a14202-2800-7000-8000-000000000001` and `…0002` (2026-10-16T00:00:00.000Z), `pub(crate)` constants reached through `ModePreset::id()`; a test reads each seeded row back through the validated deserializer and compares it to the preset. New bots take `afk`; `bots.mode_id` references `modes` with no ON DELETE action, indexed.
- **S39 (security). Deleting an account whose bot an agent may still run** writes a `releasing_bots` record (the bot, its agent, the Minecraft identity: the profile's UUID or the offline name lowercased) in the deletion's transaction, through `AccountWrites::delete`, the one delete path. While a record is open, no bot of that identity is placed anywhere, and it counts against its agent's capacity; that agent's `Removed`, a hello of its without the bot, or `agent release` closes it. A refused pending link's bot was never placed, so refusing writes no record. `account.delete` records the bot and its agent. *Rejected:* orphan bot rows, refusing the new link, an accepted risk.
- **S40 (security, low). `last_state`:** the registry keeps each bot's latest admitted report in memory, with no write per message. It reaches the database only inside transactions D commits anyway: `bot.unassign`, `bot.detach`, `agent.disconnect` (every bot that stream held) and `agent.connect` (each listed bot assigned to that agent), never backwards (`last_state_at` is the server's receipt time). Columns `last_state` (eight kinds), `last_state_reason` (paused or failed only), `last_state_at`, read back through fleet-core's `bot::LastState`. *Rejected:* memory only (a Paused bot forgotten across a server restart), a periodic flush (an exemption), a write whenever the sticky part changes (agent-driven writes).
- **S41 (security, light). The shown state** (`fleet_core::bot::shown`): `Reported` (its agent online, reported on the current stream), `AwaitingReport` (online, nothing yet on this stream), `Unknown {agent's status, its last_seen_at, last known state}` (assigned to an agent without a live stream: stale, expired, disabled, or the server just started), `Unplaced {why, sticky}`. `app::bots::BotService` reads it for E. `GET /agents` and `agent list` gain a bots count: the bots assigned to the agent and its open release records.
- **S42 (security). Placement:** live agents in enrollment order (the agent ID, which the server minted; never its name or capacity), first fit; placed bots are never rebalanced. **An agent back with less capacity** keeps the bots it runs first, then those not paused or failed, then the lowest IDs. The surplus moves under the no-two-agents rule: a bot it doesn't run is cleared at once (`bot.detach not_running`) and placed elsewhere in the same pass; a running bot at rest is left out of `ReconcileFull` and held Releasing; a running bot not at rest stays in `ReconcileFull` with desired Stopped and is unassigned only after its resting report (no bound for moves). **The 60 s bound** applies only to bots that stopped qualifying (S33). A welcome folds new placements into its one `ReconcileFull`, always sent; other agents get `AssignBot`. Free capacity: the hello's capacity minus Assigned, Releasing and open records. A bot is placed only when no live stream holds it or a bot of the same identity; a hello never gains its agent an assignment (a listed bot the database doesn't assign to it is left out and held Releasing, and S43 persists the fence).
- **S43 (security). A hello's bot the database doesn't assign to that agent** (a restored backup, a hand-edited database) gets a persisted `releasing_bots` record naming the listing agent, in its own audited transaction (`bot.stray {agent, assigned_to}`, a Failure), committed before that agent's `ReconcileFull`; it closes like any record, so the fence survives the stream's end and a server restart. *(As built after PR #52's review: the record and `bot.stray` are written in the hello's own transaction, before the stream goes live.)* A listed bot with no row and no record (an unknown identity) is fenced by its ID in memory only: persisting it fences nothing, and auditing it would let made-up IDs flood the log. *Rejected:* memory only (two agents on one account after the stream ends), assigning it to the listing agent (a hello would gain an assignment).
- **S44 (security). A `Removed` for a bot held Assigned** (one the server never released) frees nothing: it's dropped and counted like any refused report; the hold, `agent_id` and the latest report stay. An honest agent sends `Removed` only after a removal the server asked for, so such a `Removed` crossed a newer assignment; detaching would put the account on a second agent, and a compromised agent could send its accounts elsewhere while it keeps playing them. *Rejected:* detaching, dropping only the hold.
- **S45 (security). The placement gate:** right after serve starts, nothing new is placed until every agent the database shows as enabled has been welcomed since the start, or `PLACEMENT_GRACE` (90 s) has passed, whichever comes first; welcomes still get their stored assignments, and S43's fences apply. The registry starts empty, so otherwise whichever agent reconnects first takes unassigned bots another agent may still run while the database doesn't show it: a restored backup, or (with WAL and `synchronous=NORMAL`, ADR-0005) a power loss or OS crash on the server's host rolling back the latest commits. 90 s = G's keepalive (30 s) + `fleet_proto::control::RECONNECT_DELAY_MAX` (30 s, a new constant G's backoff stays within) + `WELCOME_TIMEOUT` (30 s), pinned by a test. *Rejected:* no gate, a fixed wait, waiting only for agents with assignments (misses the one whose only assignment was the lost commit), `synchronous=FULL` (overturns ADR-0005's pragmas).

### PR #52's review, fixed on the branch
Each fix with a test red first; the record in the PR.
1. **A `Removed` from an older stream never clears a newer one's bot.** A `Released` note carries its stream's generation, and `take_released` drops it once a newer stream of its agent has been welcomed (whose welcome may have given the bot back) or while the agent's stream holds the bot assigned. Before, a note requeued after a busy detach, or one that landed between `take_released` and `placement_view`, could clear the row of a bot the agent's new stream ran; if that stream then ended before its `Removed`, the bot could be placed on a second agent. Tested on paused time and over loopback, through a reconciler whose detaches fail on demand.
2. **S43's fence is written in the hello's transaction** (`AgentConnectionService::record_hello`): a listed bot that the database doesn't give the agent gets its release record and `bot.stray` before the stream goes live, so the fence never lives only in memory (while the hello is accepted, when the stream halts before its welcome settles, or when the reconciler's write fails). The row's agent is read alone (`BotWrites::agent_of`). The reconciler's own stray write stays as a backstop for a record that appears later (another agent's record of a bot the hello listed).
3. **The reconciler is watched** (`serve::spawn_reconciler`, `serve::watched`): if it returns or panics before the shutdown asked it to, that's an `error` line and the gRPC port's future ends with an error, so serve stops like a server that ended unasked (the API drains, the database closes, exit 4). Nothing restarts it.
4. **Small ones:**
   - `account.delete` records the deleted bot's agent beside the bot, as S39 says.
   - **A bot that doesn't read back is left alone** (`fleet()`'s `unreadable`, the planner's `Untouchable`): a row, or a release record, that doesn't read back no longer fails every pass. Its ID, the agent it names and, when it reads, its account are kept; it's never placed, unassigned, moved or sent anything, keeps its agent's slot and fences its account; a welcome that lists it as its own waits until it reads back (no full reconcile could keep it running, and leaving it out would remove it); the reconciler logs it at `error`, once a pass, and reconciles every other bot.
   - **An undelivered assignment is sent again** (S42's steady case): a bot whose row names a live agent that doesn't hold it (its `AssignBot` was `TooLarge` or `Unwritable`, or the stream was halted between the view and the commit) is sent again within the agent's room; one that no longer qualifies, or has no room, is recorded (`Undelivered`, logged at `info`) and settled by the agent's next hello. A `Removed` still to be cleared reads as a releasing hold in the registry's view, so such a bot never goes back to the agent that just removed it. The planner's capacity proptest counts resent bots, and found the first version overfilling an agent.

### Group E: decided by the review agents *(approved by the user at the plan review)*
One read-only agent per question, each given the options neutrally.
- **S46 (security). SSRF: the agent checks, the server doesn't.** Any Manage holder may set any address that parses (after S47's step-up). The only sound check point is the agent at connect time, on the socket fleet-mc already resolved (`ResolvedAddr.socket` in `fleet-mc/src/connector/driver.rs`, SRV included), the exact socket azalea dials: that defeats rebinding, SRV redirects and split-horizon DNS, and works for agents in other networks. Three classes:
  - *never:* unspecified, link-local (169.254.169.254 included), multicast, broadcast, reserved, benchmarking and documentation addresses, also inside IPv4-mapped, NAT64, 6to4 and IPv4-compatible forms;
  - *private:* loopback, RFC 1918, carrier-grade NAT and unique local, allowed only inside the agent's `[control_plane] private_targets` (a CIDR list, empty by default; `IpNet` moves to fleet-core for it);
  - *public:* everything else.

  Only server-sent specs are checked; standalone mode never is. A refusal is the new `ConnectFailure::Blocked`, transient and never dialled. **Built in G** (fleet-mc, so `just test-slow`); before G no bot runs through the server, so nothing dials a stored address. E records it here, in Plan.md, in the `PATCH`'s OpenAPI description and in the threat model (B4, "P10.7 (planned)"), with its accepted risks: a public address that forwards to an internal one, a hostile public server, a DNS change between connects (each connect is checked on its own resolution), and a listed network open to every Manage holder of a bot on that agent. *Rejected:* a resolve at `PATCH` time (rebinding, SRV, split horizon; the server isn't on the agent's network); rules by role (whether a target is legitimate depends on the agent's network, not on who set it); a per-bot wire flag; no policy.
- **S47 (security). Step-up per action.** The server address needs one: it sends the account, its mode's actions and later its chat to a server the person at the PC picks, and it outlasts the session. The mode switch and the five lifecycle calls don't: Control-level, nothing lost or widened, undone by the next call. Resume's possible kick of a human is one-off, since that human logging in again pauses the bot; start can kick one too, so a step-up on Resume alone would protect nobody. Step-up is per route, so the mode leaves `PATCH`: `PATCH /bots/{id} {server_address}` is a `step_up_route`, `PUT /bots/{id}/mode {mode_id}` an `authed_route` (a deviation from P11.2's text, with a Plan note). The threat model's B7 text changes, with a new accepted risk: someone at an unlocked PC can drive the bots the user may Control.
- **S48 (security). Lifecycle semantics.**
  - **Start and stop are durable:** a conditional write of `desired_state`, never dependent on the reported state.
  - **Restart, and resume or reset of a placed bot, are one-shot:** `LiveAgents::command` sends only to the live stream that holds the bot Assigned, through the registry's `send`; never stored, deferred or replayed.
  - **Resume or reset of an unplaced sticky bot is durable:** it clears `last_state*`, conditionally on the judged values and `agent_id IS NULL`, and takes the registry's kept report in the same transaction, putting it back if the commit fails, since the reconciler restores the newer of the two.
  - **An assignment returns the stored state:** `Assignments::assign` returns the row's last state from its own `bot.assign` transaction, and a new placement's restore comes from it, never from the pass's earlier read; otherwise a pass that read the row before a clear would restore the cleared Paused.
  - *Rejected:* durable commands for placed bots (they no-op while the agent keeps the bot running, or fire late after an agent restart and kick a returning human); a pending-command column; spec epochs.
- **S49 (security). The wire message:** `ServerMessage.lifecycle = 10`, `LifecycleCommand { bytes bot_id = 1; Lifecycle command = 2; }`, `enum Lifecycle { UNSPECIFIED, RESTART, RESET, RESUME }`. No correlation ID and no answer: the effect comes back as a normal `Status`, so nothing new needs `admit`. Reading refuses a non-v7 or wrong-length ID, `UNSPECIFIED` and unknown values. **For G:** match exhaustively; apply in stream order; for a bot the fleet runs, call exactly one `Fleet::{restart, reset, resume}` without filtering by state; drop one for any other bot at `debug`; a command never applies, removes or respecs a bot; never answer; drop the fleet's refusals; commands die with their stream.
- **S50 (security). The HTTP answers.** Start and stop: always 200 with the bot; a bot that can't run yet (no server, pending, reauth, a disabled owner) stores desired Running and reads Unplaced with why. Restart, resume and reset: 202 with the bot when sent, 200 for an unplaced sticky clear, otherwise 409. No-ops and refusals aren't audited.

  | Shown state | start | stop | restart | resume | reset |
  |---|---|---|---|---|---|
  | Reported (running kinds, Stopped) | 200 | 200 | 202 | 409 not_paused | 409 not_failed |
  | Reported (Paused) | 200 (stays Paused) | 200 (unassigned, stays Paused) | 409 not_running | **202** | 409 not_failed |
  | Reported (Failed) | 200 | 200 | 409 not_running | 409 not_paused | **202** |
  | AwaitingReport, held | 200 | 200 | stored sticky: 409 not_running, else 202 | stored Paused: 202 | stored Failed: 202 |
  | AwaitingReport not held, or Unknown | 200 | 200 | 409 unreachable | 409 unreachable | 409 unreachable |
  | Unplaced, sticky Paused, Failed or none | 200 | 200 | 409 not_running | Paused: **200, cleared**; else 409 | Failed: **200, cleared**; else 409 |
  | desired Stopped (any) | | | 409 not_running | (as above) | (as above) |

  `send`'s `NotConnected` or `QueueFull` after the audit commit is 409 `bot_unreachable`, and the entry stays; `TooLarge` or `Unwritable` is 500.
- **S51 (security). Stop on a Paused or Failed bot** sets desired Stopped (200): S33 unassigns the resting bot, which frees its slot, and its sticky state is kept. Refusing it would leave Resume-then-Stop, which kicks the human, as the only way to free the slot. Whether P11.9 offers Stop there is P11.9's UX.
- **S52 (security). A per-bot limit:** `[rate_limits] bot_actions_per_bot_per_min` (1–60, 5 by default: a burst of 5, then one every 12 s), keyed by `BotId` and spent in the handler after `authorize()` (so a 429 never reveals a bot to a stranger), whatever the outcome, by every call that makes the account join a server: start, restart, reset, resume and `PATCH`. Stop, the mode switch and the reads are exempt. *Why:* Standard plus the per-user limit (10/s) would allow 10 joins a second on one account: the server's throttles and bans, and Mojang join spam from the agent's address. Counted in the minute's refusal summary. A new rate limit: the user approved it at the plan review (rule 10).
- **S53 (security). Audit:** the actor, the IP, `AuditTarget::Bot`; one entry per real change, committed before any message.
  - `bot.set_server`: `server_host`, `server_port` (when given), `previous_server_host`, `previous_server_port`; host and port apart, so a 259-character address is never cut at 256.
  - `bot.set_mode`: `mode`, `previous_mode`.
  - `bot.start`, `bot.stop`, `bot.restart`, `bot.reset`, `bot.resume`: `state` and `state_reason`, the state the server knew when it acted.
  - Nothing for a no-op (as for an agent disabled already) or a refusal. *Accepted risk:* Admins read server addresses in `GET /audit` (ADR-0010's P7.13 note).
- **S54 (security). The DTO and the list.** `BotResponse {id, account: AccountResponse, server_address?, mode_id, desired_state, status, agent?}`: the account's field rule through one shared `account_response` (`owner` and `linked_at` only for Admins, the Owner and Manage holders; `level` the caller's); `mode_id` alone (P11.4 brings names, and a private mode's name mustn't leak); `agent` (`{id, name, status}`) for Admins and the Owner only, through `ViewAgents`. *(PR #54's review: `server_address` too only for Control holders and above.)* `BotStatus` is flat, with `kind: Open<reported | awaiting_report | unknown | unplaced>` and the other fields (`state`, `reason`, `since`, `online_since`, `attempt`, `restarting`, `last_disconnect {kind, key?, message?, connect_failure?, restriction?, session_server_failure?}`, `why`, `agent_last_seen_at`) filled per kind, every enum an `Open<…>`. `GET /bots` is keyset pages, newest first, filtered in SQL by `list_visible`'s rule (`BotReads::visible`, `listed`), and each row checked again with `authorize(ViewBot)`; a disagreement is a 500 that shows nothing. *Rejected:* a serde-tagged enum (not `Open`, and the OpenAPI/TypeScript renderer refuses `oneOf`); a mode name; agent details for everyone.
- **S55 (security). The two setting routes.** Bodies `deny_unknown_fields`; `PATCH`'s `{server_address}` is checked with `ServerAddress::try_from` (422 on `server_address`), `PUT /mode`'s is `{mode_id}`. An unknown mode, or one `ViewMode` refuses, is one 422 on `mode_id`, so modes can't be probed; `SetBotMode` refused is 403. One transaction re-reads the actor, the bot, the grant and the mode, authorizes again, writes only the changed column (never `agent_id`) and commits with the entry; `Change::Store` after the commit. An unchanged value answers 200 with no write, no entry and no hint. A Paused or Failed bot's new settings take effect at Resume or Reset (ADR-0010); a running bot's new server goes out as `UpdateBotSpec`, and the agent reconnects. No clearing the server in E; a route can add it later.
- **S56. fleet-client:** `bots(&PageQuery<BotId>)`, `bot(id)`, `patch_bot(id, &BotPatchRequest)`, `set_bot_mode(id, &BotModeRequest)`, `start_bot`, `stop_bot`, `restart_bot`, `reset_bot`, `resume_bot`, each answering `BotResponse`, in the existing two layers (`session.rs`, `client.rs`) and tested both ways.

### Group F: the user's choices
- **U14. An owner disabled while a grant waits for its account's flight: retryable for grants** (a genuine conflict between two of the user's decisions, asked at F's planning). The session-token service's flight reads the owner again once it holds the account's lock, so an owner disabled while a grant waits for an earlier refresh (up to the 2-minute wait bound) comes back as its `OwnerDisabled`, which Phase 9's mapping made non-retryable: the bot would fail and stay failed until a Reset, while the same owner found by the grant's own check is retryable (S33 stops the bot and re-enabling brings it back). Chosen over keeping the mapping (an accepted risk) and over making `SessionTokenError::retryable()` itself say yes: the grant code answers that one error retryable, `retryable()` stays as it is, and every other error keeps the mapping. ADR-0018's group C section has a note.
- **The user's change at the plan review:** each grant is logged at `info` (the request, the agent, the bot, the request's number, its kind, whether it was fresh and its expiry; never a token, a name or a UUID), not at `debug`: S61 writes no audit entry per grant, and a production server logs at `info`, so this line is incident response's trail of which agent received which bot's session, without a database write.

### Group F: decided by the review agents *(approved by the user at the plan review)*
One read-only agent per question, each given the options neutrally.
- **S57 (security). The grant pipeline: a queue per stream, owned by its session.** The registry's `judge` lets a request through only while the stream is reconciled, not ended and holds the bot Assigned; anything else (an unknown bot, a releasing one, one listed in an unreconciled hello, a halted stream) is denied at once, retryable. The queue (`grpc/control/grants.rs`) holds at most one waiting request per bot, FIFO, capped at `MAX_BOTS`; `GRANT_WORKERS` (4) run at once on a `JoinSet` the session's `select!` polls, so the read loop never awaits the token service; a full queue answers `SessionDenied { retryable: true }`. A newer request for a bot replaces its older one, which is never answered (the agent stopped waiting for it, S3); the two are never merged, since a fresh request answered with an older token would fail the bot `Failed(Auth)`. At the stream's end, after its switch is thrown, the waiting requests are dropped and the `JoinSet` shut down; a token flight already started goes on, on the service's own tracker. The answer path is a new `LiveAgents::answer_session(agent, generation, answer)`, modeled on `command`: converted and measured, then in one critical section the stream of that generation must live, not be ended and, for a grant, hold the bot Assigned; a full queue ends the stream `TooSlow`; session answers never go through `send` by agent. A port `ports::session_grants::SessionGrants`, implemented by `app::agents::SessionGrantService`, both under the control-plane gate; `control_service` takes `ControlPorts { connections, grants, clock }` (6 parameters; clippy refuses an 8th). *Rejected:* one request at a time (one slow account blocks every bot on its agent), one server-wide pool (an agent starves the others, and workers outlive their streams), try-acquire with no queue (a restart of 1000 bots becomes hundreds of denials).
- **S58 (security). A per-bot limit on fresh requests:** `[rate_limits] fresh_sessions_per_bot_per_hour` (1–60, 6 by default: a burst of 6, then one every 10 minutes), a governor limiter keyed by `BotId` on the injected clock (`RateLimits::check_fresh_session`). Only `fresh: true` spends it, and only once the registry found the bot held Assigned, so an agent can't spend the limit of another agent's bots; it's spent before the queue and the token service, whatever the outcome; past it, `SessionDenied { retryable: true }`, with no database read and no Microsoft call. Per bot across streams and agents, memory only; a `debug` line per refusal and `fresh_sessions` in the minute's summary; not audited. *Why 6 an hour:* an honest bot asks fresh only after a session was rejected at join, once per rejection, and its first six tries with the default `[retry]` fit the burst; a compromised agent gets 6 refreshes per bot, then 6 an hour, instead of about one per round trip, and Microsoft's 429 pauses every refresh. A new rate limit: the user approved it at the plan review (rule 10). *Rejected:* a constant (§7.4: "all configurable"), serving a fresh request past the limit as a normal one (the rejected token would fail the bot `Failed(Auth)`), no limiter (fails the requirement).
- **S59 (security). What's checked for each grant, when, and how it's read.** 1. The registry's filter (S57), in memory. 2. The pre-check on the read connections: the asking stream's own certificate by its fingerprint, naming the agent and passing fleet-core's `admit` (unrevoked, unexpired by the server's clock, agent enabled, in S24's order); then the bot's row must name the asking agent; then fleet-core's whole `placeable`, as the reconciler and `BotService` judge it, with `allow_offline`. The account comes from that row (S3). 3. The token: `session(account, fresh)` for a Microsoft account; an offline account's grant is its name. 4. At the moment of issue, fenced: inside `Store::write()` (`BEGIN IMMEDIATE`, writing nothing, then dropped), as `reach` does, the same reads and judgment again and the account unchanged; then, with the transaction still open, `answer_session`'s critical section and the queueing, in memory without an await. *Why both the hold and `agent_id`:* the row keeps its agent while the bot is Releasing, and the host's `agent release` changes rows without telling the registry. *Why the stream's own certificate:* with P13.6's renewal, the agent's latest certificate would let an old stream read Online until the sweep ends it. *Read as built:* an in-memory `try_send` under the registry's mutex isn't a network call under ADR-0015's rule for open transactions.
- **S60 (security). Which denials are retryable, and what a denial says.** Every denial the grant code makes itself is retryable (not held, assigned elsewhere, the agent not admitted, not `placeable` for any reason, a full queue, past the fresh limit, its own read failing): each races with something that sets it right without a sticky state (the reconciler and S45's gate, S33's stop, the sweep). The token service's errors map by `retryable()` (Phase 9's decision), except `OwnerDisabled` (U14); the pre-check runs right before the service, so it only sees active Microsoft accounts with enabled owners and never answers `Offline`. Non-retryable is then left for lasting refusals the service finds itself: `reauth_required` or `refused` from a flight (§6 row 5), an unusable stored token, a corrupt row, `Audit`. The wire stays as is (`retryable` only): the agent acts only on the flag, users see why through `Unplaced{why}`, the account's status and `Failed(session_denied)`, and reasons on the wire would tell a possibly compromised agent about its accounts. One line per denial with a fixed `reason` and the error's text: `debug` for the grants' own and the service's `BackingOff`, `InFlight`, `ChangedMeanwhile`, `ShuttingDown`, `Interrupted`; `warn` for `Microsoft`, `TimedOut`, `Seal`, a busy or failing store; `info` for `NotActive`, `NotFound`, `Envelope`, `StoredToken`, `OwnerDisabled`; `error` for a corrupt or unstorable row and `Audit`.
- **S61 (security). No audit entry for a grant or a denial.** A grant changes no row; the only possible recipient of an account's token is the agent its assignment entries name (`bot.assign` until `bot.unassign`, `bot.detach` or `agent.release`) while its stream was up (`agent.connect` to `agent.disconnect`), and every new token writes `account.refresh` already. An entry per grant would be a write per connect, competing for the one write connection in a reconnect storm, at a rate a hostile agent sets. *Rejected:* an entry per grant (above), entries for denials (made-up bot IDs would flood the log, S43's reason), capped `security.` entries (a "not held" also happens to honest agents, S28).
- **S62 (security). The agent's managed provider** (`fleet_agent::managed::credentials`). A send-only port `SessionLink::send(SessionRequest) -> Result<LinkGeneration, Unsent>` that never waits (`NoStream`, `QueueFull`); G's reader calls `answer(SessionAnswer)` and `link_ended(generation)`. A table of waiting requests (number → bot, generation, reply) behind a `std` mutex held only to insert or remove; the entry goes in before `send`; an unknown number is dropped at `debug`, another bot's answer at `warn` while its request keeps waiting; a drop guard removes an entry when the actor drops the future; numbers from 1 by compare-and-swap that never wraps. Its own bound is the runtime's `session_request_timeout` (30 s). A failed `send` or a stream's end fails the waiting requests at once, retryable. A token whose expiry is within the connect timeout is retryable with a `warn` about the clocks; the clock is the run's `RuntimeClock`. Logs carry IDs and times; `Debug` shows only counts. *Rejected:* a request/response port (correlation would move into G), two channels with a router task (one more task, and a full answer queue drops grants), an automatic fresh request on expiry (hides a refresh from the state machine, spends S58's budget).
- **S63 (security). The agent reuses a grant only while it can't ask the server.** The provider keeps each bot's last grant handed to a request still waiting (an online session in its `SecretString`, or an offline name), and hands it out again only when `send` says `NoStream`, for a request that isn't fresh, while more than the connect timeout is left; with a stream, it always asks. Requests waiting when a stream ends fail retryable and are never answered from a kept grant; late answers are never kept. A fresh request for the bot, any `SessionDenied` for it, `forget(bot)` (G: a removal or a spec with desired Stopped), `forget_all()` (G: `UNAUTHENTICATED` or a permission `Reject`, before stopping the bots), its expiry and the process's end wipe it. *Why:* §6's known limit and the accepted risk "Session tokens outlive server outages" presume it; ADR-0013's "never hand out a token that expires within the connect timeout" does nothing without a copy on the agent; asking whenever a stream exists keeps every server check in charge. *It changes a guarantee's wording:* S32's "a release proves the old agent can never join or rejoin the bot (… no grant)" reads "… no grant, and none kept once its process ended", and "a release takes the operator's word" gains that a host that's only cut off may rejoin its bots with kept sessions until they expire. *Rejected:* no reuse (any outage strands every bot that gets kicked), reuse with a stream up (bypasses the server's checks while they could refuse).
- **S64 (stability). serve builds the service and stops it within its deadline.** Built in `control_plane_services` (only with `[grpc]`) over the one `ReqwestMicrosoftAuth` (its `Arc` cloned before the link flows take it) and the vault. `app_with` creates serve's root token, returned as `App::shutdown`; `serve()` uses it, and `SessionTokenService::new(ports, &shutdown)` keeps a child of it, so no refresh starts after the signal. A task on serve's `JoinSet` waits on a child of the token, then runs `shutdown()` bounded by `timeouts.drain` (the deadline minus `DATABASE_CLOSE`), so the database keeps its 5 s; flights still running then are left with one `warn` naming how many (`SessionTokenService::running()`; a rotated token one of them hadn't stored is lost, as in a crash), and the exit stays 0. No order is needed against the gRPC sessions. *Rejected:* awaiting it unbounded inside `close` (a slow Microsoft makes the stop exit 4 and skips the database's close), a longer deadline (overturns ADR-0015's).

### Group F: reconciliations *(for the user's review)*
- **R39.** The grant service queues its own answers (S57's `answer_session`, from inside S59's fenced transaction), so the `SessionGrants` port returns nothing; the session answers its own denials (the filter, a full queue, past the fresh limit).

## Consequences
- **Easier:**
  - Agent and server handle only validated values; every message from the other side passes fleet-core's constructors once, at the stream's edge.
  - A wire change can't slip in: the snapshot shows it next to the protocol version.
  - A forgotten redaction fails to compile, and a new field named like a secret fails a test.
  - Later groups build on a protocol whose every refusal is tested and named.
- **Harder:**
  - Every new mode action needs a proto message and two conversion arms, next to its JSON.
  - A generated message that holds a secret can't be built with struct-update syntax.
  - The protocol's structure is written twice: in the .proto files and in `fleet_proto::control`.

## Alternatives considered
- **The phase boundary** (U1's other options): a minimal bot screen in Phase 10, before live events and the design pass; ports and fakes, with the security core proven only against fakes and Phase 10's real-account check gone; P11.1 and P11.2 before P10.5, which needs a stand-in for "reconciled".
- **protox 0.10.0** (U2): newer by eight days, with a fix for input we never parse.
- **Fewer groups,** e.g. P10.6 with the agent client or P11.2 with the reconciler: the two most security-sensitive pieces would share a review with the largest ones.
- The rejected options of S1–S9, each listed with its decision above.
