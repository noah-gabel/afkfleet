# 0019. The control plane: conventions, Phase 10 refinements

- **Status:** Accepted
- **Date:** 2026-10-15; groups B and C 2026-10-16
- **Related:** Plan.md Phase 10 (P10.1–P10.10), P11.1, P11.2, P11.9, P12.1, P12.2, P12.4, P12.6, P13.2, P13.4, P13.5, P13.6, §4, §5, §6, §7.5, Appendices A to D; ADR-0002, ADR-0010, ADR-0011, ADR-0013, ADR-0014, ADR-0015, ADR-0016, ADR-0018

## Context
Phase 10 connects agents to the server: enrollment with a server-signed certificate, one gRPC stream per agent over mutual TLS, the scheduler and the reconciler, short-lived session grants, the agent's client and the server's batched ingest. The stream crosses the project's sharpest trust boundary after the public API. An agent host is one of the attackers in the threat model, and the server hands that stream the only Minecraft tokens that ever leave it.

Before any code, the plan found one conflict between the user's phases: P10.5, P10.6 and P10.8 need P11.1's `bots` table (and `chat_messages`), and Phase 10's DoD ("pressing Start in the app brings a bot … Online") needs P11.2's start endpoint and P11.9's screens. The user decided it (U1). Every other open question went to its own read-only review subagent, given the options neutrally (CLAUDE.md's step 10). The user approved their decisions (S1–S9) at the plan review and added two notes for later groups. Each later group asks its own questions in its session and adds its decisions here.

### Decided by the review agents *(approved by the user at the plan review)*
- **S1 (security). Certificate renewal stays in P13.6,** which already plans it ("renew at 2/3 of the lifetime"), with P12.6's runbook. Group A leaves `RenewCertificate` out of the proto: a new RPC later breaks no agent. Phase 10 only keeps the way open: `agent_certs.agent_id` is indexed but not unique (B); the SAN's agent ID comes from the server's record (B); the agent writes its key and certificate atomically, owner-only, on its `/data` volume (B); a connection needs a fingerprint that's neither revoked nor expired (C); disable revokes every fingerprint, and `GET /agents` shows `not_after` (P10.10); an expired certificate joins P10.9's rejections. *Why:* it's the user's recorded plan; building renewal next to P13's threat-model review is safer than adding the path a stolen key would use to the biggest phase; a unique `agent_id` now would force a table rebuild then. *Rejected:* building it in Phase 10 (overturns P13.6), dropping it (Owner-only re-enrollment every 60 days per agent).
- **S2. The validated messages live in fleet-proto,** in `fleet_proto::control`, next to `generated` and never inside it: one `AgentMessage` and one `ServerMessage` built from core types, each read with `TryFrom` from its generated envelope and written back the same way. Agent and server never match on generated oneofs. What exists only on the wire stays in fleet-proto; what is stored, shown or used by a policy goes to core. *Why:* it mirrors the HTTP side, where fleet-api-types holds the DTOs and the server's services see core types; core stays the pure domain; P13.2 gets two fuzz targets that reach every conversion. *Rejected:* protocol enums in core (transport types in the domain, a second chat-failure enum there); matching on generated types in both binaries (validation repeated, unfuzzable).
- **S3 (security). Correlation.**
  - **`SendChat`** carries a new core ID, `ChatRequestId` (v7), which the server's chat service mints through `Clock` and `SecureRandom` (P11.3); `ChatSent` and `ChatFailed` repeat it, and the agent maps it to the runtime's `ChatTicket`. *Not a u64 counter:* an outcome buffered across a server restart would meet the restarted counter. *Not the HTTP `RequestId`:* it names one HTTP request, never an entity (ADR-0015).
  - **`SessionRequest`** carries the agent's own number (`SessionRequestId`, a `NonZeroU64` counted from 1 per process), which `SessionGrant` and `SessionDenied` repeat with the bot. The agent drops an answer it no longer waits for. *Not the bot alone:* the server may take 2 minutes, the agent waits 30 s, and a late grant from before a rejection could answer the next `fresh` request.
  - **`SessionRequest` names no account:** the server takes it from its own assignment, so "an agent gets tokens only for its own bots" stays the server's decision.
  - **Restart, reset and resume** get a message with P11.2 (E), as a new oneof case, together with P11.2's own questions about them.
- **S4 (security). A mode crosses the wire as structured messages** that mirror `ModeDefinition`: `Step { action, schedule, probability }`, a oneof of the ten actions, a oneof of the two schedules. Reading rebuilds a `ModeDraft` and runs `ModeDraft::validate`; a step whose action or schedule this version doesn't know is refused. *Why:* JSON stays the stored format alone (ADR-0010), so a database migration that rewrites stored modes can't change the protocol; serde_json's errors quote their input, and fleet-proto's never do. *Rejected:* the JSON form in a string (a third JSON use, migrations coupled to the wire, quoting errors on the agent); `google.protobuf.Struct`.
- **S5 (security). Times and IDs.** Times are `optional int64` milliseconds since the Unix epoch (`*_unix_ms`): reading refuses a missing one and one outside 0000-01-01T00:00:00.000Z to 9999-12-31T23:59:59.999Z, the database's and the API's range; writing drops anything finer than a millisecond and refuses a time outside the range. IDs are 16 bytes: a bot's, an account's, an agent's and a chat request's must be v7, a Minecraft profile's non-nil. No well-known types, so prost-types stays build-only. A heartbeat carries no time: the server stamps `last_seen_at` with its own clock. *Why:* every value round-trips exactly, with no text parser facing untrusted input; whatever an agent sends, the server can store. *Rejected:* string times and IDs (canonical-form checks, a third time parser, twice the size); `google.protobuf.Timestamp` (a run-time dependency, nanos to check).
- **S6 (security). Text from Minecraft is cleaned again; validated values are strict.** Received chat and a kick's key and message are rebuilt through `IncomingChat::from_parts` and `DisconnectReason::kicked`, which clean and cap them; only structural faults are errors. `truncated` is the agent's flag OR the server's own cut. Validated values are refused, never repaired, in both directions: a chat message must arrive trimmed, a server address in its written form, conflict texts, names and versions as their constructors accept them (a set's order and duplicates are accepted). *Why:* a compromised agent gains nothing from dirty text it can't store, while a stricter rule would drop an older agent's report (a duplicate-login Paused kick) whenever the sanitizer's lists grow; repairing a human's text silently changes it (ADR-0013). *Rejected:* refusing text that cleaning would change; counting cleaned messages inside the conversion (it can come at ingest).
- **S7 (security). Secrets stay out of `Debug`.** The build script skips prost's derived `Debug` for each message that holds a secret (`OnlineSession` now, `EnrollRequest` in B), listed in its `REDACTED`. `fleet_proto::redact` writes their `Debug`, which names only what isn't sensitive and ends with `..`, and a `Drop` that wipes the secret. The conversion moves the token out with `mem::take` into `SecretString::from(&str)`, which allocates exactly its length, and wipes the original. The enclosing oneof's and envelope's derived `Debug` call the hand-written one, so forgetting it fails to compile; `missing_debug_implementations` stays out of the generated module's allowances. A test fails on any field named like a secret (`token`, `secret`, `password`, `key`) outside a redacted message, unless it's on a not-secret list with a reason (a kick's translation `key`). *Accepted residual:* the buffers tonic, h2 and rustls decode and encode into can't be wiped, as ADR-0018 accepted for hyper's. *Rejected:* no `Debug` at all (it spreads to every type that holds a message, and would need the allowance loosened); convention only (prost's derive prints the token); a wrapper message; hand-written wire code.
- **S8 (security). No agent labels in v1,** in no config key, proto field, core type or column: nothing schedules by them through Phase 13. **Capacity** is the agent's `[runtime] max_bots`, sent in the hello as the new core `AgentCapacity` (1–1000, the config's range); 0 or above 1000 is refused, never clamped. Free capacity also counts the bots unassigned whose `Removed` hasn't arrived. *Why:* capacity decides which agent gets which bots, and so which session tokens; labels can come later as an additive field. The threat model records that only Owner-only enrollment, mTLS and revocation stop an agent inflating its capacity. *Rejected:* labels now (six layers without a consumer); a bare proto field (unvalidated input).
- **S9 (security, low). "The proto codegen check"** (P0's promise in CLAUDE.md's commands table and the justfile) is a pinned wire-schema snapshot. build.rs generates the code into `OUT_DIR`, as P10.1 says, and renders the compiled descriptor as text: every message's fields with number, name, label, type and oneof, reserved numbers and names, every enum, the service with its streaming flags, and the redacted messages, without comments or source positions. `tests/protocol/schema.rs` snapshots it under `PROTOCOL_VERSION`, so a wire change shows in review; no recipe or CI job is added. The protocol stays at version 1 until the first release (P12); after that, a snapshot change needs a decision about the version. *Rejected:* committing generated code with a freshness check (contradicts P10.1's build script, churns on every prost bump); dropping the promise.

### As built (group A)
- **The crate** `fleet-proto` (depends only on fleet-core): `proto/fleet/v1/{agent,bot,chat,mode,common}.proto`, package `fleet.v1`, with the `AgentControl` service and its `Connect` stream; `build.rs`; `src/{lib.rs, control/, convert/, error.rs, redact.rs}`. The files live under `crates/`, the only folder the agent image's `.dockerignore` admits. It joins `stable_crates`.
- **The build:** `protox::compile`, then `tonic_prost_build::configure()` with client and server, `build_transport(false)`, `skip_debug` for `REDACTED`, and `compile_fds`. The schema is rendered through protox's re-export of prost-reflect, so the build needs no other crate. `main` returns a `Result`.
- **`fleet_proto::generated`** carries `#[allow(clippy::pedantic)]` and nothing else: the generated code trips only pedantic lints (`doc_markdown`, `must_use_candidate`, `default_trait_access`, `missing_errors_doc`), none of the workspace's denied ones.
- **`fleet_proto::control`:** `AgentMessage` (`Hello`, `Heartbeat`, `Status(BotSnapshot)`, `Event(BotEvent)`, `SessionRequest`), `BotEventKind`, `ChatFailedReason` (the runtime's five delivery failures and six refusals), `SessionRequestId`; `ServerMessage` (`Welcome`, `Reconcile(Vec<Assignment>)`, `Assign`, `Unassign`, `Update`, `SendChat`, `SessionGrant`, `SessionDenied`, `Reject(RejectReason)`); `MAX_BOTS` (1000, pinned equal to `AgentCapacity::MAX`). `Welcome`'s heartbeat interval is 1 s–5 min on the wire.
- **The leaf conversions** are trait impls between core's and the generated types: `BotSpec`, `ModeDefinition`, `StickyState`, `BotNotification`, `DisconnectReason` and `IncomingChat` are written with `From`; `BotState` and `BotSnapshot` with `TryFrom`, since they hold times. `SessionCredentials` converts inside `SessionGrant`.
- **Errors:** `ConvertError { field, index, problem }`, where `field` is `Message.field` in the protocol's names, `index` the position in the innermost list (a bot in a hello or a reconcile, a mode's step), and `Problem` one of `Missing`, `Unknown`, `WrongLength`, `NotV7`, `Nil`, `OutOfRange`, `TooMany`, `Duplicate`, `NotExact`, `InvalidToken` or a wrapped core error, none of which carries input.
- **fleet-core:** `id::ChatRequestId`; `value::AgentCapacity` (`NonZeroU16`, `TryFrom<u32>`) and `value::AgentVersion` (1–64 of `[0-9A-Za-z.+-]`, starting with a letter or digit, like `AgentName`).
- **Tests,** each red first against compiling stubs with the real signatures:
  - **fleet-core:** 29 for the two values, 19 of them red against stubs that refused everything; the others check refusals and the errors' fixed texts. The capacity property passed at first, since uniform `u32`s almost never land in 1–1000; its input is weighted toward the range now, and it went red. `ChatRequestId` is one more instance of the ID macro, covered by the two tests that list every ID type.
  - **fleet-proto:** `tests/protocol/` (round trips, decoding any input, one case per rejection, redaction, the schema) and unit tests of the helpers. 147 of 164 failed against stubs that refused every read and wrote default messages. The 17 that passed checked what a stub happened to answer (an expected `Missing`, the helper `required`, the constant pin, the error's formatting) or held vacuously while everything was refused (the decode properties, the guard).
  - **Temporary mutations** showed those red, each reverted and checked by checksum: the agent's `truncated` flag dropped (the clean-text property), a probability wrapped instead of refused (the mode property), the heartbeat read without its range (any server bytes), an unspecified enum read as unknown and a missing value read as unknown (seven rejection cases), the error without its position, a refused token named in the error, a field named `password` outside a redacted message (the guard), and a time read without its range (the time property and its unit test).
  - **Found by a mutation:** an encoder that swapped `AgentBusy` for `ShuttingDown` passed every property, since random cases reach one reason of eleven in one event kind of seven too rarely. Five exhaustive tables now cover every value of each mapped enum, and swaps in three of them went red. The time property's input is weighted toward the range's edges too: uniform `i64`s rarely land in chrono's range outside years 0–9999.
  - **The snapshot** `protocol__schema__wire_schema.snap` was read before it was accepted.
- **Found during the build:**
  - The zeroizing `Drop` forbids struct-update syntax on `OnlineSession`, so its test cases change a valid session through a helper.
  - Integration tests read `OUT_DIR`, so the schema test and the guard read the build script's rendering directly.
  - chrono without features has no `to_rfc3339`; the range test compares the date's parts.

### Group B: decided by the review agents *(approved by the user at the plan review)*
- **S10 (security). Every key is Ed25519 from getrandom bytes:** the CA's, the server's, the agent's, and the only key a CSR may carry. 32 bytes from the `SecureRandom` port (getrandom on the agent) are wrapped as PKCS#8 v1 (RFC 8410's fixed prefix) and loaded with `PKCS_ED25519`; `KeyPair::generate*` is never used, since it draws from aws-lc's own RNG. *Rejected:* rcgen's generator (an exception to rule 4 and the port); P-256 alongside (a second key type for no gain).
- **S11 (security). The profiles:** a 16-byte serial from `SecureRandom` (first byte 0x40–0x7F); validity from an hour before the clock's time to the lifetime, in whole seconds, within 1970–9999. The CA (`afkfleet CA`, ten years, path length 0, keyCertSign), the server (`afkfleet server`, one year, serverAuth, 1–8 names from `--dns`/`--ip`), agents (`afkfleet agent`, `[grpc] agent_cert_lifetime_days`, clientAuth, one SAN `urn:uuid:<agent ID>` from the server's record). `pki server-cert` renews the server pair from the same CA.
- **S12 (security). `pki init` and serve's reading:** the four `[grpc]` files only; every problem checked first; `create_new` temp files (0600 on Unix), synced, published with `hard_link`, which never replaces; a failure removes only this run's names. Serve reads the four through `secret_file` before the runtime and refuses a missing file (with `pki init`'s name), more than one certificate or key, a CA certificate that isn't a CA's, a key that isn't its certificate's, and a server certificate the CA didn't sign; an expired server certificate is an `error`, and serve runs on. `just dev-server` creates the dev PKI once.
- **S13 (security). One gRPC port** on `[grpc] bind` (127.0.0.1:7443 by default), only while `[grpc]` is configured: TLS with the server certificate, the CA as the root for client certificates, which are optional, but verified when presented. B serves `AgentEnrollment`; C adds `AgentControl` behind a gate that refuses a call without a verified client certificate. No compose change in B.
- **S14 (security). Enroll's limits and answers:** 8 KiB decoded, 16 KiB encoded (tonic's own `OUT_OF_RANGE` above), no compression; a CSR of 1–4096 bytes; 15 s in the handler, below the agent's 20 s; a 10 s handshake, 16 calls per connection, connections of at most 60 s plus 20 s. `[rate_limits] enroll_per_ip_per_min` (1–60, 5) is spent first, keyed like the HTTP limits (an IPv6 client by its /64). Every answer carries `x-request-id`; each case has one fixed message (the table in `grpc::enrollment`). Logs never hold the token, its hash, the CSR or the peer's address.
- **S15 (security). The bundle:** one line, `<token>.<CA fingerprint>`, 146 characters; the agent reads it from stdin only (a terminal refused, at most 1 KiB, wiped), checks `[control_plane] ca_cert_file` against the pin before any connection, and trusts that one certificate as tonic's only root. A wrong CA file shows both fingerprints and sends nothing.
- **S16 (security). A token stands for one new agent:** Owner-only, step-up, no body, 15 minutes, at most 20 pending, no list or revoke in B. The agent's name comes from its own config, unique ignoring case among enabled agents; every Enroll creates a new agent with a server-minted ID; no token re-issues an identity. Signing runs in `spawn_blocking` before one write transaction that checks the token again, stores the agent and its certificate's fingerprint, and uses the token conditionally; a certificate that loses a race is dropped unsent. The answer carries no CA certificate.
- **S17 (security). What's audited:** `enrollment_token.create` (the Owner and the IP over HTTP; no actor from the host; `expires_at`, `via`); a successful Enroll commits `agent.enroll` (no actor, the peer's IP, the agent, its fingerprint, `not_after`, name and token ID) and `enrollment_token.use`; a real token that's expired, used or whose creator lost the right is an `agent.enroll` Failure with its reason, at most 10 per token. Unknown and malformed tokens, refused CSRs and rate-limited calls aren't audited.
- **S18 (security). An identity that exists is refused, never replaced:** nothing may be at `key_file` or `cert_file` (a file, a folder, a dangling link) and no `<file>.tmp` lock; the folders must exist. The key is written into its temp file before the call; afterwards both are linked with `hard_link`. A failure after the server answered is exit 3, naming the agent to disable.
- **S19. The agent's command:** `afkfleet-agent enroll --config PATH`, the same `config::load` as `run`, `[control_plane]` required. `url` is `https://host:port` (no credentials, path or query, a port other than 0) and the three files absolute and distinct, for `run` too; `run` keeps refusing `[control_plane]` until P10.7, pointing to `enroll`. Timeouts: 5 s to connect, 5 s for the handshake, 20 s for the call, 30 s in all; the answer at most 16 KiB; no retry. Fixed texts per failure, never the server's message.
- **S20 (security). Windows:** the agent's and `pki init`'s files inherit their folder's permissions there, since std gives them no owner-only mode; both commands say so on Windows, and the README and the threat model record it. No ACL crate and no `unsafe`.
- **S21 (security). The order of Enroll's checks** (a tie-break agent, with both rationales): the peer's address, the rate limit (both in the gate), the conversion, the token, the name, the CSR, the transaction. The token comes before the CSR, so x509-parser, signatures, blocking threads and the CA key stay away from anyone without a token; the name comes after the token, so names can't be probed without one. *Accepted:* a token holder can probe agent names, as an invitee can probe usernames (ADR-0016). *Rejected:* S14's first answer, the token last, which puts the parser in front of the internet.

### Group B: reconciliations *(for the user's review)*
- **R1.** `enrollment_tokens.created_by` is NULL for the host's tokens; the creator's re-check applies only when there is one; the cap of 20 counts every pending token.
- **R2.** Without `[grpc]` the token route answers 404, after the step-up check, as `POST /accounts/offline` does while it's off; the host command refuses with "the control plane is off".
- **R3.** `enroll`'s exit codes are 0, 1, 2 and 3 (S18's case).
- **R4.** The dev agent dials `https://127.0.0.1:7443`, and the dev server certificate names `localhost`, `127.0.0.1` and `::1`.
- **R5.** `pki server-cert` never overwrites either.
- **R6.** Ed25519 only (S10 over S14's P-256).
- **R7.** The token route answers `{id, bundle, ca_fingerprint, expires_at}`.
- **R8.** The agent's timeouts and its answer cap are S14's shared constants.
- **R9.** `max_connection_age` bounds every connection while `Enroll` is the port's only service; C replaces it with a bound for connections without a client certificate, or records the residual. As built (PR #49 review): with the grace set, tonic 0.14.6 sends no GOAWAY at 60 s but cuts the connection, calls in flight included, at 80 s; removing the grace isn't a fix either, since tonic then polls the finished timeout future again.
- **R10 (security), decided by a review agent during the build.** `EnrollResponse` carries the certificate as `string certificate_pem` instead of `bytes certificate_der`. rcgen 0.14 can't PEM-encode a certificate it didn't make, and the agent has no `base64`; the server holds rcgen's PEM of the same DER it fingerprints and stores. The agent stores the text it received only after checking it: exactly one PEM section, a certificate, with nothing outside its `BEGIN` and `END` lines; a client certificate the pinned CA signed, valid now (rustls's client verifier, the check C's port makes); and its own key. *Rejected:* a DER file (pushes the same choice to P10.7, after the wire is merged); `base64` in the agent (needs the user's approval when a rule-respecting option exists); a hand-written encoder (works around the registry); both forms on the wire (two copies that could disagree). Cheap to change until the first release.

### Group C: decided by the review agents *(approved by the user at the plan review)*
One read-only agent per question, each given the options neutrally; they read CLAUDE.md, Phase 10, this ADR and the threat model in full, then the code.
- **S22 (security). The connection bound (R9).** The listener wraps every accepted socket in its own `Bounded` IO before tonic's TLS, and cuts it at 80 s (S14's effective value) unless a `Lift` is held. A Connect stream takes the lift only after its identity, its hello, its registration and Welcome, and drops it when it ends, so the 80 s start again then. tonic's `max_connection_age` and its grace go. The connection's info is the listener's own `Connection` (the peer's address and the bound's handle), read as `TlsConnectInfo<Connection>`; Enroll's gate takes the peer from it. *Why:* no crate, S13's one port, and a revoked or never-welcomed certificate can't hold a connection either. *Rejected:* any verified certificate lifting the bound (a revoked key would hold connections forever), an own TLS acceptor (a crate, and the same flaw), no bound (a slow-body Enroll unbounded), a second port (overturns S13). *Residuals:* an admitted agent's connection can carry up to 15 more calls with no age; connections per address aren't counted.
- **S23 (security). Liveness.** HTTP/2 keepalive on both ends, no proto change. `[grpc] heartbeat_interval_secs` (1–60, 10) and `heartbeat_timeout_secs` (2–300, 30, at least twice the interval) build a validated `Heartbeats`; the server's keepalive pings every interval and closes a connection whose ping isn't answered by the timeout (hyper's server pings idle connections too). Every agent message that converts resets the stream's deadline. *Rejected:* a server heartbeat message (a proto change; it can't close a silent TCP connection, and it queues behind a reconcile), both. *Later:* G's channel keeps alive every 10 s with a 20 s timeout, while idle too, and beats on Welcome's interval.
- **S24 (security). The handshake and its answers.** The gate checks the certificate first, then mints the request ID, then spends the limit (S30). Before the stream opens: the fingerprint's row, then revoked, expired (`now >= not_after` by the server's clock), disabled, and only then the SAN (exactly one `urn:uuid:` of the row's agent); all five failures are one `UNAUTHENTICATED`. After it opens (`x-request-id` in its headers): the first message within 10 s (`HELLO_TIMEOUT`; the agent waits 30 s, `WELCOME_TIMEOUT`), read by `fleet_proto::control::read_hello` (a hello at all, then `protocol_version` equal to `PROTOCOL_VERSION`, 0 included, then the conversion), then the name, byte for byte. `Welcome` gains the agent's ID. A second hello ends the stream; after a Reject the stream ends OK. One fixed message per case; the hello's name, the peer and certificate bytes are never logged. *Why:* nothing is parsed for anyone unauthenticated, identity answers are uniform as enrollment's are, and exact equality fails safe. *Rejected:* a version range, a server version in Welcome, case-insensitive names, a reason per identity failure.
- **S25 (security). Sizes and queues.** `fleet_proto::control::MAX_AGENT_MESSAGE_BYTES` 8 MiB (the largest legitimate hello is 4.09 MiB: 1000 snapshots with kicks at their caps) and `MAX_SERVER_MESSAGE_BYTES` 128 MiB (the largest reconcile is 65.3 MiB, its conflict texts at their cap), for both ends. `fleet_proto::codec::BoundedCodec` (build.rs's `codec_path`, outside `generated`) counts a hello's running bots through a decode-only view of zero-sized entries and refuses more than 1000 before prost builds them: an empty entry is 2 bytes on the wire and about 112 in memory. Each stream's outbound queue holds 2048; a send never waits: over the limit is `TooLarge` (the stream stays), a full queue is `QueueFull` and ends the stream, so the agent resyncs. No rate limit on what an agent sends. *Rejected:* tonic's defaults (a 4 MiB decode limit refuses a legitimate hello), the amplification as an accepted risk, chunked hellos (a protocol change).
- **S26 (security). One stream per agent: a second is refused.** A second Connect while the agent's stream lives gets `Reject(AlreadyConnected)` after its hello checks; the live stream is untouched, and the slot frees only when its session task has ended. A message on the live stream after a refusal proves two holders of one identity: an `error` line and `security.agent_identity_conflict`, at most once an hour per agent. *Rejected:* replacing (a thief could push the real agent out, and two processes would kick each other's accounts), replacing after silence, a per-process ID.
- **S27 (security). A permission that ends mid-stream.** A per-stream timer ends the stream at its certificate's `not_after`, and a 5 s sweep (one query for every admissible fingerprint) ends any stream whose certificate is revoked or expired or whose agent is disabled; each ends with `Reject(AgentDisabled | CertificateRevoked | CertificateExpired)` ahead of anything queued. The disable service commits, then ends the stream. *Rejected:* a stream living on past its permission, a grace, refusing a host disable while serve runs (it can't be detected).
- **S28 (security). Reports about bots.** The registry keeps, per agent, the bots it holds (`Assigned` or `Releasing`), empty until D fills it. One function admits every message: a status or an event for a bot it doesn't hold is dropped, counted and logged at `debug`, and the stream stays; a releasing bot passes only its `Removed`, which ends the hold; every session request in C gets `SessionDenied` with `retryable` true (false would fail the bot for good). A hello's bots that aren't held are ignored. Housekeeping logs one line per agent with refusals. *Rejected:* ending the stream (honest races exist, and it amplifies a hostile agent), refusing the hello.
- **S29 (security). Presence.** Nothing is written per message. An accepted hello: one transaction checks the certificate and the agent again, writes the capacity, the version and `last_seen_at` (never backwards) and commits `agent.connect` before Welcome; if it fails, the hello is refused as busy. The stream's end writes the last message's time and `agent.disconnect` with its reason. *Rejected:* memory only (the columns would stay empty), unaudited writes and a periodic flush (new exemptions).
- **S30 (security). Connect's limit, and which refusals are audited.** `[rate_limits] connect_per_cert_per_min` (1–60, 10), keyed by the presented certificate's fingerprint, spent in the gate before any parse or read. A known certificate's identity refusals (`revoked`, `expired`, `disabled`, `san_mismatch`, `name_mismatch`) are `agent.connect` Failures, at most 10 per agent in a rolling 24 hours; an unknown certificate is an `error` line, never audited. *Rejected:* no limit (security rule 3), a limit per address (agents behind one NAT), a permanent cap (one episode would hide a later theft).
- **S31. The agents' API and the host commands.** `GET /agents` pages like every list and shows every agent: `{id, name, enabled, status, capacity, version, connected_since, last_seen_at, not_after, created_at}`, the status `online`, `offline`, `expired` or `disabled` (an `Open<…>`), `not_after` the latest of the unrevoked certificates. `POST /agents/{id}/disable` (step-up) answers 200 with the agent, the same with no entry when it's disabled already, and works with `[grpc]` off; `agent.disable` records the name, the certificates revoked and `via`. The host gets `agent list` and `agent disable --id`. fleet-client's agents methods come with P11.9.

## Consequences
- **Easier:**
  - Agent and server handle only validated values; every message from the other side passes fleet-core's constructors once, at the stream's edge.
  - A wire change can't slip in: the snapshot shows it next to the protocol version.
  - A forgotten redaction fails to compile, and a new field named like a secret fails a test.
  - Later groups build on a protocol whose every refusal is tested and named.
- **Harder:**
  - Every new mode action needs a proto message and two conversion arms, next to its JSON.
  - A generated message that holds a secret can't be built with struct-update syntax.
  - The protocol's structure is written twice: in the .proto files and in `fleet_proto::control`.

## Alternatives considered
- **The phase boundary** (U1's other options): a minimal bot screen in Phase 10, before live events and the design pass; ports and fakes, with the security core proven only against fakes and Phase 10's real-account check gone; P11.1 and P11.2 before P10.5, which needs a stand-in for "reconciled".
- **protox 0.10.0** (U2): newer by eight days, with a fix for input we never parse.
- **Fewer groups,** e.g. P10.6 with the agent client or P11.2 with the reconciler: the two most security-sensitive pieces would share a review with the largest ones.
- The rejected options of S1–S9, each listed with its decision above.
